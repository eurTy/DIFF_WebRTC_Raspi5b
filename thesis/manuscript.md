# 1 绪论

## 1.1 问题来源

工业远程观察不是单纯的视频播放问题。操作者希望知道关键区域是否仍处于可辨识状态，也希望所见画面能反映当前而非数秒以前的状态。当上行带宽不足或无线链路出现间歇停顿时，保持整幅图像的高质量可能使传输时间增加；简单降低全局分辨率又可能使接触边缘、工件位置或局部状态变化难以辨认。这两个目标并不总能同时满足，因此需要明确任务、测量代价，并在给定资源下作出可解释的取舍。

本文以树莓派、USB 摄像头和普通电脑构成的低成本实验平台为对象。既有系统已经实现视频采集、网络传输、浏览器显示和只读状态监测，但既有结果不能直接证明新研究系统的性能。研究首先冻结旧版本并建立可核验的整合清单，再在空目录、独立 Git 历史和新容器中建立新系统。这样可以区分设备已有能力、此次新增实现和仍未完成的工业验证，避免把历史项目的测试数据当作新方法的证据。

本文不将摄像头作为光电开关、编码器或安全联锁的替代品。对于单一到位判定，专用传感器通常更直接；视频的潜在用途在于提供无法由一个二值信号表达的上下文，如观察遮挡、位置关系和异常过程。本文研究的是这种观察链路的信息分配，不实施机器运动控制，不声称取得真实产线良率、节拍或停机时间的改善。

## 1.2 相关研究与研究边界

AccMPEG 研究面向远端视觉推理的编码质量分配，利用任务相关的重要性估计减少无效传输[1]。AWStream 从流分析任务出发研究带宽与分析精度之间的配置关系[2]。两者说明，整幅图像的重建质量并非所有任务的唯一目标。本文借鉴任务相关资源分配这一既有思路，但没有复现其模型训练和完整实验，也不以这些论文中的性能提升比例作为本文结论。

信息年龄研究将接收端掌握信息的生成时刻与当前时刻联系起来，用于描述状态更新的新鲜程度[3]。这启发本文同时报告“收到一帧时的延迟”和“任意观察时刻的帧龄”。一条每隔数秒才成功传输一帧的链路，即使成功帧的延迟很小，也未必适合连续观察。因此，本文把无帧、停顿和超时纳入时间覆盖率，而不是只统计成功样本。

本文采用的语义定义是任务级的工程定义：由使用者给定区域名称及重要性，结合区域变化和高质量更新等待时间进行调度。它不等同于语言模型的场景理解、自动工步识别或联合信源信道神经编码。图像差分不是人工智能模型。选用这个定义是为了使资源决策可解释、计算成本可测，并能在已有硬件上完成对照实验。

## 1.3 工作内容与贡献定位

本文的工程工作包括独立系统的实现、四种传输策略的可控比较、跨设备软件时间戳测量、真实 TCP 限速中继和旧系统隔离验收。主要研究问题是：在相同任务区域与输入条件下，重点区域优先分配能否改善任务信息保真度；动态优先级相对固定权重产生什么收益与损失；以帧龄而非仅以成功帧延迟评价时，结论是否改变。

本文不声称提出新的压缩标准、拥塞控制理论或工业安全方法。自包含区域组合、确认反馈与只保留最新输入属于可组合的工程设计。本文的价值在于把这些设计落实为可运行、可测量、可回退的系统，并公开失败条件和原始数值结果。所得结论只适用于实验所覆盖的输入、链路与资源配置，不能无条件推广到 H.264、硬件编码平台或实际工厂。

# 2 需求分析与测量指标

## 2.1 应用假设和资源约束

设想的应用是制造现场设备维护人员对局部过程的远程复核。观察者可以在画面中指定工序 A 和工序 B 的关注区域，调整相对权重，在网络变差时优先保留这些区域的细节。上述场景是需求假设，而非已经接入的生产线。实验中的细线、运动色标及背景纹理是人工构造的可重复输入，不代表某个真实设备故障类别。

实验硬件不增加 PLC、STM32 或电机控制板。树莓派承担新发送端，电脑承担浏览器和测试接收端。新服务仅使用独立端口 8088；旧服务继续运行于原目录及端口。容器限制为最多 1 CPU 和 64 个进程，使用非 root 用户、只读根文件系统与临时目录。现场内存控制器没有提供可依赖的容器内存限制，因此不将 Docker 显示的 0 B 误认为零内存消耗，也不声称实施了有效的硬内存隔离。

{{table:constraints}}

帧率和有效载荷上限是实验参数，不是对物理无线速率的测量。默认重建画布为 1280×720，但背景图像可能经过降采样，重点块也可能采用不同分辨率和 JPEG 质量。因此，“720p 画布”不等于全画面维持原始 720p 细节。与旧版保持当前画质的要求不同，新研究系统明确将空间质量分配作为实验变量，旧版画质不作改动。

## 2.2 延迟和帧龄的定义

令源时间戳为 s，接收端完成软件解码或绘制的时刻为 r，两个主机的时钟偏移估计为 θ，则一次成功帧的软件段延迟由式 2 1 给出。该端点随输入方式而改变：合成源从生成开始计时；只读共享内存源从旧采集发布时刻计时；独立 USB 适配器从读取完成时刻计时。三种数值不能不加区分地横向比较。

{{equation:latency}}

视频显示后，旧画面不会因为没有新包而自动变新。任意观察时刻 t 的帧龄取决于最近一次已经显示的源时间戳。该定义见式 2 2，停顿期间它随时间增加。系统没有有效校时或尚未显示首帧时，应呈现未知状态，而不能显示为 0 ms。

{{equation:age}}

实验采用 250 ms 作为预先声明的观察新鲜度阈值，并按 100 ms 网格统计时间覆盖率。250 ms 仅用于本实验比较，不是工业控制安全门限，也不表示人体操作或具体工艺一定可接受该延迟。不同工艺应依据风险、变化速度和可接受误差另行确定阈值。

## 2.3 图像与任务信息指标

重建误差分别在重点区域和背景计算。重点区域指标按指定权重汇总，背景指标独立报告，防止仅展示局部收益而隐藏全景损失。采用 PSNR 是因为其定义清晰、可重复计算；但像素误差不等同于人对异常的可辨程度。对于完全一致图像，程序用 99 dB 作为有限存储上限，并在结果元数据中明确标注。

{{equation:psnr}}

为了获得可核验的任务代理指标，合成输入包含两个小色标。接收端比较色标颜色状态与质心位置；颜色一致且位置误差不超过 3 像素视为成功。原图与重建图使用同一规则提取色标，以隔离传输失真造成的变化。该指标是人工标记保真度，不是神经网络检测准确率，也不是工件尺寸测量精度。

新鲜任务覆盖率同时要求当前画面足够新鲜、任务色标保真，并按区域权重计算得分。它用于避免“清楚但陈旧”和“及时但无可用细节”被单独的好指标掩盖。在预算极低的情况下，这一复合指标可能明显下降，即使成功帧的延迟仍然很小。

## 2.4 验收条件

系统验收包括协议边界、有效载荷完整性、会话生命周期、软件计时与页面渲染。原系统完整性作为独立验收项目：旧 Git main 不变，旧部署核心文件不变，旧服务仍运行。新系统的成功运行不得以停止旧采集、修改旧目录或复用旧镜像作为代价。

浏览器验收覆盖 1440、1024、390 和 320 像素宽度，检查画面非空、像素随帧变化、页面无水平溢出、四种策略可切换以及数值记录可导出。截图检查只能证明测试时的显示状态，不能取代连续时延测量。真实摄像头截图留在私有目录，不提交公开仓库。

# 3 系统总体设计

## 3.1 数据流与模块划分

发送端依次执行获取最新输入、计算区域优先级、选择编码档位、构造自包含帧包和等待确认。接收端校验元数据，完整解码全部图像块，再将同一帧的背景与重点块合成为 720p 画布。只有本帧完成处理后才发送确认。校时使用另一条轻量连接，以避免时间请求直接排在视频大消息之后。

{{figure:architecture}}

模块边界使图像源、编码策略、传输协议和实验评价相互分离。离线实验可以绕过网络直接测量率失真关系；网络实验使用相同编码策略而更换接收方式；真实摄像头适配器只改变输入来源，不改变区域包格式。这样能够定位问题究竟来自编码选择、发送反馈、网络服务时间还是显示环节。

{{table:modules}}

## 3.2 输入与旧系统的隔离

默认合成源由固定随机种子生成纹理背景，并在已知区域绘制运动色标。参考图像可以根据种子和帧号重建，因此无需把原始视频文件上传到公开仓库。输入复杂度分别由不同纹理幅度控制。相同帧号与种子生成相同图像，但不同策略的实时传输会跳过不同数量的源帧，网络实验并非严格逐帧配对。

只读共享内存适配器实现文档化的外部格式，不导入旧项目的应用模块。读取时先取得 48 字节头部，确认写序号为偶数，再读取指定长度的 JPEG，最后重读头部并比较。若写入尚未提交、前后头部不一致、长度越界、时间戳过旧或图像尺寸不符，则拒绝该输入。打开权限为只读，容器挂载也为只读，形成应用和部署两层边界。

现场共享目录权限为 0750，新容器默认用户无法进入该目录。接入时只为新容器追加目录现有的组编号，并保留只读挂载，不修改旧目录权限、不改变所有者，也不通过 root 绕过边界。该故障与修复说明，图像格式正确并不代表实际部署已经可用，权限模型同样是测控系统接入的一部分。

独立 USB 适配器使用 V4L2 后端并保留最新一帧，但本次不与旧采集器争抢同一设备。V4L2 缓冲区时间戳的含义取决于驱动及时间戳标志，不能把读取完成时间默认当成曝光时刻[6]。本文共享输入测得的是发布之后的处理与传输时间，未覆盖摄像头曝光和 USB 驱动缓冲阶段。

## 3.3 通信方法选择

本系统选用 WebSocket 承载应用帧包。其优点是浏览器原生支持双向消息，便于发送参数、确认和独立时间戳，并能清楚检查消息边界。WebSocket 建立在 TCP 之上[4]，因此可靠性并不意味着低延迟保证。一个大的旧消息发生重传时，后续消息仍可能被阻塞。

本文没有从零编写 TCP、JPEG 编解码或浏览器网络协议，而是采用 aiohttp[8]、OpenCV[7] 和浏览器标准实现。应用层新增的是帧包、预算策略和会话状态机。虽然还可以选择 WebRTC、不可靠数据报或 H.264 ROI 编码，本科实验需要先建立可复现的比较基础；没有进行这些方法的同条件对照，就不能宣布当前组合是全局最优方案。

## 3.4 自包含帧包

二进制消息由协议魔数、元数据长度、JSON 元数据和一至五个 JPEG 图像组成。第一块必须覆盖完整画布，其余块必须位于画布内。接收端校验总长度、块数、整数范围、有限时间戳以及 JPEG 起始字节，拒绝尾随数据和无完整背景的消息。协议上限为 4 MiB，元数据上限为 48 KiB。

自包含设计的直接收益是每一帧可独立恢复。接收端无需依赖前一次成功收到的重点块，连接中断后也不需要恢复变化域参考状态。其代价是全景和局部可能重复编码相同区域，压缩效率不一定高于成熟的帧间编码。本文用可解释性、恢复简单和低依赖换取这部分冗余，后续仍需与帧间编码比较。

# 4 语义优先调度与反馈实现

## 4.1 四种对照策略

全帧基线维持 1280×720、JPEG Q85，不主动牺牲空间质量。全局自适应从预定义的分辨率和质量档位中选择，使整幅图像共同退化。固定区域策略将带宽优先分配给权重更大的区域。动态策略在权重基础上加入局部变化和等待时间，以减少低权重区域长期得不到高质量更新的情况。

{{table:policies}}

所有策略使用相同源接口、消息格式、确认语义和目标帧率参数。全帧基线仍受有效载荷节奏约束；“全帧”表示不改变空间编码配置，而不是无限制向 socket 写入数据。对比时必须区分配置上限、真实发送有效载荷、线上的协议开销以及最终收到的帧率。

## 4.2 区域重要性与变化度

区域由归一化坐标、名称和权重描述。权重限定在 1 至 10，区域数为 1 至 4，总面积不超过画布的一半。该面积限制是当前实现的实验边界，用于防止把大多数画面都声明为重点，从而失去差异化分配意义；它不是通用工业规律。

每个区域转换为 32×32 灰度小图，计算与上一处理帧的平均绝对差并归一化，得到变化量 c。等待时间 a 从上次得到成功确认的高质量区域更新开始累计。动态优先级采用式 4 1，其中变化项与等待项都有上限，避免单次异常值无限放大分数。

{{equation:priority}}

系数 12、250 ms 和等待项上限 12 是本原型的预设参数，不是由真实工厂数据学习得到的最优值。权重、变化和老化相加的方式便于解释，但不能证明对所有任务最优。局部光照变化、摄像头移动或背景运动也会抬高差分量，因此变化不等于工艺事件。后续应把任务定义与变化检测可靠性分开评价。

## 4.3 有效载荷预算

给定 kbps 上限 R 和目标帧率 f，初始单帧预算由式 4 2 计算。编码器为元数据预留空间，先编码完整背景，再按优先级尝试放入重点块。如果包大小超过预算或最高优先级区域未被选中，则向更低档位尝试。最低档仍不满足时明确标记超预算，而不是隐去该样本。

{{equation:budget}}

为避免长期停留在最低档，编码器周期性尝试提升一个档位。此设计计算量可控，但属于保守探测：链路突然恢复后，空间质量可能需要多次确认才能恢复。候选档位搜索也会产生额外 JPEG 编码成本，所以实验同时记录编码次数和编码耗时，不能仅用节约字节数判断方案有效。

## 4.4 确认反馈与发送节奏

每个会话最多保留一帧等待确认。发送端只接受类型、帧号完全匹配的确认，布尔值不能冒充整数帧号。服务时间较大时缩小预算；连续多个较快确认后缓慢增大预算，且不超过用户设定上限。反馈量包括传输、接收端解码和反向确认路径，因此只是应用服务时间，不能称为物理信道容量估计。

发送周期同时满足目标帧率和有效载荷限制，见式 4 3。图像源在下一周期重新读取最新输入，未发送的旧源帧不排成长队。在极低预算下，这能限制持续入队，却不能消除已经交给 TCP 的旧消息，也不能保证每帧都在新鲜度阈值内到达。

{{equation:pacing}}

一次树莓派浏览器测试发现，低帧率等待若仅使用 sleep，关闭的旧会话可能延迟释放资源，导致快速重连撞上两个会话的上限。修复后，等待期间继续读取控制帧，收到关闭就及时退出；浏览器也等待旧连接关闭后再发起新连接。针对低预算全帧模式增加了断开释放测试，避免修复只对默认模式有效。

进一步的实机观察发现，单次确认反馈容易把孤立停顿误判成长期容量下降，使预算快速缩小后停留在低质量档。为检验这一问题，新增五样本中值反馈作为独立可选模式。控制器保存最近五组服务时间与包长，按服务时间排序，选择中间样本及其对应包长，再执行原有预算更新。样本不足五个时保持初始预算。这样可以抑制少量离群点，但会延迟对持续拥塞的响应，不能预先保证性能改善。

中值滤波是常见的稳健处理方法，本文不将其包装为新算法理论。单次反馈实现及实测数据以独立 Git 标签保存，后续消融实验只改变反馈输入，不改变区域权重、编码档位或任务判据。浏览器可以切换两种反馈，实验接收端检查服务端确认的模式，防止实际仍运行旧实现却把记录标为新方法。

## 4.5 失败状态与可信边界

输入连续失效、确认超时或参数非法时，会话以明确状态退出。没有有效校时时延迟显示未知；帧龄超过阈值时保留过期提示。画面不应因连接显示 connected 就被判定为实时，也不应在断线时把陈旧画面作为正常观测证据。

服务器限制同时视频会话数、时钟会话数与时钟请求频率，并检查浏览器 Origin。该检查不能替代用户认证：非浏览器客户端可不发送 Origin，本系统也没有实现公网证书、身份和访问审计。因此部署边界是可信局域网，不应直接公开到互联网。系统没有 GPIO、串口或 PLC 写入接口，传输错误不会触发设备动作。

# 5 实验设计与计量方法

## 5.1 证据分层

本文将证据分成三个层次。第一层是协议、生命周期和输入边界的自动化测试，用于证明实现按约定处理正确与错误输入。第二层是合成输入的离线配对实验，用于隔离网络对图像质量比较的干扰。第三层是真实 TCP 连接和树莓派运行实验，用于观察处理、传输、解码与确认组成的完整软件链路。

电脑预实验、树莓派合成实验、真实摄像头接入验收分别保存，不混为一个总体。被并行浏览器测试影响、且用于发现重连问题的首轮树莓派数据保留为 pilot，不纳入主表。保留失败数据的目的在于使排除条件可追溯，而不是通过删除差样本获得更好的均值。

## 5.2 离线配对实验

离线实验覆盖三种背景纹理、512、1024、2048 kbps 三档预算以及四种策略，每个单元取 30 帧，共 1080 个编码样本。每个策略接收相同种子和帧号的输入。调度等待时间采用明确的合成时间步，不让电脑运算快慢影响区域老化决策；实际编码耗时仍由高精度计时器记录。

配对实验能回答在指定编码档位和任务图案下如何分配空间质量，不能直接回答无线链路中的停顿概率。构造图案带有细线和小色标，天然强调局部细节，因此所得优势可能在自然场景中减弱。相邻帧高度相关，1080 个样本不是 1080 次相互独立的网络试验。

## 5.3 实际限速链路

限速中继在电脑本地建立一条真实 TCP 连接，向树莓派转发浏览器协议的数据。视频下行按小块字节节奏发送，反向确认不人工限速。每个方向使用有界应用缓冲区。该方法不需要管理员修改无线接口 qdisc，也不会把旧项目一并限速；但它只是应用层排队与节奏控制，不等价于射频丢包、干扰或 TCP 网络层仿真。

操作系统定时器和调度会使实际中继速率低于配置上限，因此结果同时保留有效载荷数量和全部中继字节数。网络试验使用固定随机调度种子打乱策略顺序，以减轻固定顺序与时间变化的混淆，但短时 Wi-Fi 波动仍无法完全消除。真实系统受到原有服务、主机调度和无线环境共同影响，不能只归因于某一个策略参数。

每个测量单元预留 3 s 热身，之后统计 12 s。输入按 30 fps 时间轴生成，发送端根据自身节奏取最新帧。不同策略接收到的帧号不相同，因此任务得分受当前色标相位影响；这是采用离线配对实验与实时实验互相补充的原因。不同纹理种子属于不同场景，不应误标为同一场景的独立重复试验。

正式受限链路共安排两轮，每轮对两个纹理场景、三档带宽和四种策略各测一次，总计 48 个有效测量单元。第二轮改变策略顺序，相当于每个场景条件有两次重复。第二轮初次执行的第八个单元在校时阶段超时，未能形成有效测量，原脚本退出；已保存的七个单元保留，随后断点续测，并把这次失败及新增重试规则写入实验说明。有效单元数量不包括校时不完整尝试，这一排除限制了对系统总体可用率的推断。

## 5.4 四时间戳校时

设客户端发送、服务端接收、服务端发送、客户端接收的时间戳依次为 t0、t1、t2、t3。偏移估计与往返时延按式 5 1 和式 5 2 计算，其基本关系与 NTP 的四时间戳方法一致[5]，但这里是应用层实验实现，不是完整的 NTP 协议栈。

浏览器保留近期样本并选取较小 RTT 的有效值；样本不足或过期时停止给出延迟。网络实验在每个单元前后校时，记录偏移变化。路径不对称会导致偏移误差，最小 RTT 只能减少排队污染，不能证明两个方向完全对称。因此，跨主机的单向延迟始终是带假设的估计值。

实验另给出诊断裕量：初始最小 RTT 的一半加上前后偏移变化的绝对值。将这一裕量加到帧龄后再计算保守新鲜覆盖率，以展示接近门限的结论有多敏感。这个量不是经过校准的 95% 置信区间，也不能覆盖所有时钟漂移和时间戳语义错误。当校时 RTT 或前后漂移偏大时，结果必须带警告解读。

## 5.5 不确定性和结果汇总

误差来源包括时间戳端点不含曝光、反向网络路径不对称、任务代理指标本身的局限、JPEG 解码和浏览器绘制时间、以及 100 ms 帧龄采样的离散误差。相邻采样点的状态具有相关性，不能把每个点当成独立伯努利试验来制造过窄的置信区间。

主表按带宽与策略列出实际完成的场景数和测量时长。P50、P95 若来自不同单元，不简单平均后称为总体分位数；需要汇总原始成功帧再计算，并说明这仍然以成功接收为条件。时间覆盖率则按每个单元的观察时长计算，关闭或无帧区间不得从分母移除。

# 6 实验结果与讨论

## 6.1 功能验收与部署证据

{{results:validation}}

新系统在树莓派中采用独立容器和桥接网络，旧采集容器、网关容器与两个主机服务继续保留。归档检查确认旧部署源码包、运行镜像包和 SQLite 在线备份可读取，数据库完整性检查返回 ok。整合版在新目录对比 39 个核心文件，未发现与旧部署的源码差异。

这些检查说明本次改造遵守了版本与目录边界，不等于对所有旧功能进行形式化证明。容器运行、源文件一致和可恢复归档分别覆盖不同风险，不能相互替代。论文代码和结果只提交公开所需的源码、合成数值和文档，现场图像、数据库及凭据不进入 GitHub。

## 6.2 配对质量结果

{{results:rd}}

全帧基线保留更多全景细节，但它的有效载荷在低预算下显著超出单帧目标。全局自适应通过降采样降低字节数，相应丢失细小色标和线条。区域策略可以把有限字节集中在指定位置，不过未选中的区域只能依靠低质量背景，不应将这些区域当作始终保真。

动态优先级和固定权重的区别主要在于分配时序，而不是采用了完全不同的图像编码器。等待项会让低权重区域获得更新机会，也会减少高权重区域获得全部资源的时间。因此，动态策略的加权平均任务得分可能略低于固定权重。若应用目标仅是最大化一个静态高权重任务的平均得分，固定策略可能更合适；如果低权重区域也有最大等待约束，就需要另一个公平性指标。

## 6.3 树莓派受限链路结果

这些结果应首先从信息新鲜度与任务保真度的组合解读。成功帧延迟下降不必然说明体验改善：预算被不断压低时，传输包会变小，延迟可能降低，但任务信息也可能消失。反过来，全帧基线即使保真度很好，长时间的传输与停止更新也会导致新鲜任务覆盖率降低。

第一阶段的单次确认控制器对间歇停顿较敏感。一次较慢的确认既可能来自持续容量不足，也可能来自 Wi-Fi 短时排队；仅凭该反馈不能区分二者。当预算连续缩小而恢复条件不满足时，系统可能停留在最低编码档，影响任务效果。本文将这种现象视为基线控制器的局限，不把所有较低延迟都解释为优化成功。第 6.5 节在独立对照中检验中值反馈改进，不回写本节基线数据。

## 6.6 失效边界与适用条件

本方法适合任务区域可明确指定、背景细节允许退化、且观察不是安全关键闭环的场合。对于全景搜索、新目标随时出现在任意位置、或背景同样具有关键意义的任务，固定 ROI 可能遗漏重要信息。对于大幅镜头运动和剧烈照度变化，简单变化度也不能稳定表达任务重要性。

当前协议以单连接可靠消息传输为基础，出现长重传时仍会陈旧。自包含帧包只能简化下一帧的恢复，不能撤回已经进入 TCP 的字节。未来若改用支持过期丢弃的传输方式，必须重新设计帧完整性、分片丢失和时钟消息，不宜仅替换接口名称后宣称解决了队头阻塞。

低资源系统也必须度量计算开销。JPEG 重点块数量增加会带来额外裁剪、缩放和编码，自包含背景又会重复表示部分像素。高算力平台可能更适合成熟帧间编码和硬件加速。在未加入这些基线之前，本文结果只说明当前四个配置策略的差异，不支持“优于所有视频通信方法”的结论。

# 7 总结与后续工作

## 7.1 工作总结

本文围绕受限条件下的远程观察建立了独立原型，把任务区域、空间质量分配、确认反馈和信息新鲜度纳入同一可测量流程。旧系统经过冻结和只读一致性校验，新系统使用独立代码历史、镜像、端口和数据目录。实验以合成任务代理建立可重复参考，又用树莓派真实 TCP 链路揭示软件端点、无线抖动和反馈策略之间的关系。

结果的核心意义不是获得一个脱离条件的最低延迟数值，而是证明评价必须同时包含任务信息、陈旧时段和资源成本。区域分配存在收益，也存在背景质量下降和低权重区域取舍；动态策略不保证所有指标同时优于固定 ROI。论文把这些边界与原始记录一起保留，形成可以继续验证的工程基础。

## 7.2 与测控专业的联系

本课题的专业训练重点是采集链路时间端点的识别、跨设备同步误差的分析、测量指标的定义、受限资源下的信息调度，以及实验过程的可重复性。它能够作为设备远程观察或自动化测试工具的一部分，但没有替代设备本体、传感器校准和安全控制逻辑。

面向制造业设备维护、自动化测试与系统集成岗位，能够展示的实际能力是 Linux 服务与容器管理、只读接入既有系统、网络与时序故障定位、质量与延迟的联合验收，以及基于数据说明方案边界。这些能力来自已实现和已测试的环节，不应在简历中扩写为已完成 PLC 调试、真实故障诊断或生产线节拍优化。

## 7.3 后续实验与改进

后续应优先增加真实工件与标定真值，定义区域内允许的最大观察等待时间，并进行相同场景的多次独立重复。可以研究区分长期容量不足与瞬时抖动的反馈机制，以及在质量下限和更新频率之间联合选择的控制策略。参数优化应先设定验证集和评价目标，避免只针对已经看到的样本反复调参。

通信方法还应加入成熟 H.264/WebRTC、可过期数据报和不同设备算力基线，测量任务保真度、CPU 成本、恢复时间和失败概率。若引入 AI，宜首先将模型用于异步建议任务区域或离线分析，不把高耗时推理强行放入每帧关键路径。模型接口必须保留置信度、超时与人工覆盖，不因增加 AI 标签而牺牲可解释性。

最终的工业应用需要在真实网络、访问控制和设备安全要求下重新验收。本文初稿尚需依据学校格式、导师要求和补充实物实验修改；学校、作者、学号和导师信息没有凭空填写。当前可交付物是有源码、数值结果和明确限制支撑的本科研究初稿，而非已经经过答辩或工业认证的终稿。
