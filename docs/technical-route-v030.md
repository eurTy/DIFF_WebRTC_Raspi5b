# 0.3.0 技术路线与验证边界

课题保持为《受限环境下的语义自适应视频传输系统设计与实现》。本轮重点是修复弱网退化、补齐恢复与配置保存、完成现存传输路径的工程对照和较长时间实测。0.2.0 路线与旧论文冻结保留，本文说明增量，不把新方法倒填到旧数据。

## 1. 面向测控的研究对象

将视频视为远程观察的测量信息，而不是安全控制信号。资源不足时，同时评价三件事：信息是否新鲜、关键区域是否可辨、故障后是否能恢复。仅降低收到帧的平均延迟会掩盖冻结；仅提高局部清晰度会增加积压；仅丢弃所有旧帧也不能消除失联期间没有新信息的问题。

现有设备即可完成验证，不新增控制板，不做小车或仪表读数演示。工业应用定位是远程设备状态复核与工序观察，不能据此宣称已经完成生产线故障诊断、设备闭环控制或安全认证。

## 2. 实现路径

```text
旧采集发布的最新帧（只读）
 -> 序号/时效检查与一次共享解码
 -> 人工任务权重 + 局部变化 + 高质量刷新等待时间
 -> 同帧全景与重点块的预算编码
 -> 单帧保守启动，健康交付时才扩大为两帧
 -> 浏览器解码、过期拒绝、一次合成
 -> 显示确认调节预算，丢弃确认不刷新区域高质量年龄

独立校时 -> 延迟估计 / 帧龄 / 完整事件导出
连接恢复 -> 已应用配置持久化 / 可取消重试
主机只针对已知 USB 设备恢复故障进行有限启动重试
```

现用研究系统仍是 WebSocket/TCP；本轮没有把新版视频服务换成 WebRTC。旧系统的 WebRTC 只作为已存在方案的只读实测基线。

## 3. 控制器修正

设目标周期为 `T = 1000 / fps`，预算上限为 `Bmax = kbps * 1000 / 8 / fps`，确认服务时间为 `S`，最近一帧字节数为 `L`。`S` 包含传输、往返路径和接收解码，不是纯网络容量测量。

- 初始窗口为 1，避免在未知链路容量下先形成双帧积压。
- `S > 1.25T` 时立即回到单帧，并令 `B = max(min(1400, Bmax), min(0.78B, 0.85LT/S))`，不再等待三个慢确认。
- `S < 0.8T` 的连续快速确认达到三次后，使用 `min(Bmax, 1.12B + 100)` 探测恢复。
- 中性区间连续达到二十次后，使用 `min(Bmax, 1.02B + 20)` 低频探测，避免长时间停在低预算。快速与中性计数必须分开，不能将交替反馈误当成连续快确认。
- 只有预算达到上限的 90% 且连续八次快速确认后，才允许两个在途帧。其余情况保守为单帧。
- 当预算低于上限的 90%，无法容纳重点块时恢复历史最低上下文回退行为，避免盲目保持背景清晰度阻碍关键块预算的后续恢复。

这是工程启发式反馈，不是已经证明稳定性和最优性的拥塞控制定理。单帧控制器仍保留为独立对照，不能为了突出新策略而修改基线。

## 4. 可论证的本科贡献

1. **任务细节与信息新鲜度联合评价。** 不只报告码率、FPS 和延迟，同时记录新鲜时间内的关键标记辨识代理分数。失败候选揭示“更清晰的背景”不等于“更有用的任务信息”。
2. **带保守回退的应用层反馈实现。** 将最新帧输入、有界窗口、基于交付时间的快速降预算、分离的恢复计数与 ROI 刷新确认语义串联，并用消融与负面结果说明适用边界。
3. **从断源到显示的可验证恢复链路。** 区分 USB 源故障、传输故障与参数错误；持久化已应用配置；长测分段保留全部数据，并从实际绘制事件重建帧龄。

贡献应定位为系统设计与实验验证，不能称为首次提出 AoI 或创造了新的工业通信协议。人工 ROI 是当前语义来源，不是 AI 检测。AI 保留为非实时关键路径的区域/权重建议接口，尚未实现。

## 5. 评价方法

### 弱网配对

固定配置 1200 kbps / 10 fps，独立中继限制为 512 或 128 kbps；三种合成纹理、两种控制器，随机顺序完成十二个单元，每个正式测量 20 秒、预热 3 秒。接收端点是 Python JPEG 解码完成，不是浏览器显示。不同纹理不是同场景的多次独立重复，不给出不成立的统计显著性结论。

### 原生传输路径对照

对旧服务采用 WS、WebRTC、WebRTC、WS 的顺序，各测量 60 秒。输入都是摄像头原生 720p JPEG，测量至浏览器 `img.decode` 完成。检查实际视频数据通道的 `ordered=false` 与 `maxRetransmits=0`，不凭页面名称推定协议属性。只记录必要的候选类型与传输统计，不导出 ICE 地址。

两种发送节奏和实际码率不同，现场画面与无线信道也没有固定，因此这是现有实现的工程对照，不是同码率下的协议因果实验，更不能据此宣称 TCP 普遍优于 WebRTC。旧网关在客户端结束会话后按既有监督策略回收进程，测试记录应与运行日志一起解释。

### 长时间运行

浏览器每分钟下载一次数字轨迹并去重合并，防止超过页面 10000 帧历史容量后丢失前半程。通过总显示数加丢弃数校验记录完整性。现场截图保留于忽略的 `runtime/`，不公开上传。

对于实际显示帧，按 `A(t) = D_i + t - t_i` 重建直到下一次显示的帧龄；`t_i` 是绘制完成时刻，`D_i` 是该帧的软件延迟估计。丢弃帧不更新当前画面。积分计算 `A(t) <= 250 ms` 的时间占比，未知校时与冻结时间仍在总时间分母内。不能使用每 250 ms 才刷新的界面帧龄直接代替连续时间结果。

所有软件时间戳仍依赖校时路径近似对称，不能替代曝光到屏幕发光的光学测量。500 ms 迟到拒绝也不是网络或硬实时保证。

校时尚未完成或已过期时，系统可以显示延迟未知的输入，不能执行可靠的 500 ms 年龄判断；未知值不当作零延迟或新鲜样本。到达延迟分位数包含已校准的丢弃帧，但不包含无数值的未知帧；汇总另列未知数量，连续帧龄的总时间分母保留未知和冻结区间。

## 6. 仍存在的限制

- 低预算背景会降采样，720p 重建画布不是全图原生细节保证。
- 128 kbps 下本次关键标记代理任务分数仍为零；不能以“画面还在动”声称任务可用。
- 512 kbps 下新旧策略的任务分数存在差异，新策略尚未实现所有指标同时占优。
- TCP 底层排队无法由接收端丢帧撤回；WebRTC 部分可靠通道也不能替代合理的发送节奏与重组截止期限。
- 局域网原型没有身份认证、HTTPS、公网接入与安全联锁能力。未人为拔插摄像头，也未做物理射频丢包或光学校准。
- 本轮结果不能作为半天/全天稳定性、工业认证或生产率提升的证明。实际测量时长与数值以结果文件为准。

## 7. 后续严格实验

先在隔离实验服务中对相同码流、相同发送节奏、相同容量/RTT/丢包轨迹比较 TCP 与成熟 WebRTC 实现，再决定是否替换当前路径。若采用数据通道，需要有界分片重组、到期淘汰、乱序确认与关键块重传策略，不能无限发送大 JPEG。

围绕一种具体任务建立人工真值和盲测，例如关键状态变化的可辨性及发现时间；不要把合成彩色标记的成绩直接当作工厂故障诊断准确率。保留原生质量、全局自适应、固定 ROI、任务 ROI、保守回退等消融，并增加相同场景重复次数、容量阶跃重复和基础 RTT 变化轨迹。本轮另有一组连续容量阶跃探索，不能代替多重复统计。

协议选型依据：[RFC 8831](https://www.rfc-editor.org/rfc/rfc8831)；成熟候选实现接口：[aiortc API](https://aiortc.readthedocs.io/en/latest/api.html)。库只作为后续实现参考，本轮未向生产镜像加入 aiortc。

## 8. 续测暴露的系统级边界

2026-10-14 的现场观察出现了视频冻结、SSH 重置和秒级 ICMP 往返。两端都连接同一个 5 GHz 接入点、短测分别访问网关无丢包，并不能推出两无线客户端之间转发正常。树莓派本机状态请求约 1.3–6.2 ms，而树莓派到电脑的一组 ping 最高约 2312 ms。探测时段不是严格同步，不能据此精确分摊每一跳延迟，也不能排除驱动、接入点、客户端系统负载等原因。

这种现象应作为论文的失效分析，而不是从结果中剔除。接收端约 40 ms 的典型到达延迟，可以与长时间画面冻结同时存在；必须同时给出连续帧龄、未知校时占比、断连次数与到达帧分位数。恢复后丢弃旧帧只能避免继续播放旧信息，不能补回失联期间缺失的测量信息。

下一轮先用不经过摄像头和编码的双向小包探测、另一终端或另一接入点对照定位网络，再在固定路径上进行同码流传输实验。当前不通过增加重传缓存、隐藏帧龄或随意修改内核参数制造“更稳定”的表象。长测的完整性与是否达到稳定性目标分开判定，具体数字见本轮结果目录。
