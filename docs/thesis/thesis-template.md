# 摘要

远程设备维护中，视频能够提供环境与动作背景，但单独的视频画面不能说明数据是否新鲜，也不能解释视频停止究竟来自采集端还是状态通道。针对已有树莓派视频系统缺少状态关联、运行诊断和故障证据的问题，本文设计并实现一种面向设备远程运维的视频与状态协同监测原型。系统以树莓派 5、USB 摄像头和普通计算机为平台，在保持 1280×720 原生 MJPEG 图像的条件下，保留 WebRTC DataChannel 链路并采用有界最新帧 WebSocket 拉取方式，新增独立只读状态服务与时钟探测通道。以共享内存发布时间、驱动时间戳和浏览器解码时间构建分段时延估计，以画面年龄和状态质量刻画数据新鲜度；通过带去抖和回差的规则建立异常触发与恢复事件，并关联事件前后状态和现场图像。

本文首先审计 Linux 采集、调度、网络与进程监督配置，再实现共享内存重开、采集超时退出、服务权限约束和日志减量。实验使用真实视频和主机状态，不以软件模拟运动代替实物。{{ABSTRACT_RESULTS}} 三轮受控采集暂停中，告警触发时间为 1.390～2.258 s，恢复确认时间为 1.172～1.568 s，状态通道持续可用。结果表明，该原型能够在现有硬件上完成现场视频、节点状态和事件证据的统一观测，并对延迟与数据过期给出可解释的显示。其价值是提高远程排查的可观测性和实验可复现性，而不是提供确定性控制或安全保护。本文的跨端时延仍为基于网络时钟估计的驱动／发布至解码时间，尚未测得光学端到端延迟，也未证明真实工厂维护效率的提升。

# Abstract

Video provides useful visual context for remote maintenance, but a video stream alone does not indicate whether the displayed information is fresh or whether an interruption originates in the acquisition process or in the status channel. This thesis presents a video and status monitoring prototype built with a Raspberry Pi 5, a USB camera, and a personal computer. Native 1280 by 720 MJPEG frames are preserved. The implementation retains the WebRTC DataChannel path and provides a bounded latest-frame WebSocket path, an independent read-only observer, and a separate clock-probing connection. Timestamped capture metadata and browser decoding callbacks support explicitly scoped latency estimates. Frame age and status quality distinguish delayed or missing observations from valid zero measurements.

The observer samples real Linux counters, applies debounced diagnostic rules, and stores alarm and recovery events with preceding and following state samples and a correlated image. The implementation was examined through software regression tests, browser layout and failure tests, a repeated communication comparison, and controlled capture-process pauses. In three pause experiments, detection took 1.390 to 2.258 seconds and recovery confirmation took 1.172 to 1.568 seconds, while host status remained available. The work demonstrates an inspectable laboratory monitoring workflow, not a deployed industrial control system. Timing estimates exclude display scan-out and have not been validated by an optical reference instrument. No motor, PLC, production equipment, or claimed safety function is included.

Keywords: remote maintenance; measurement system; video transport; age of information; incident evidence; Raspberry Pi

# 第1章 绪论

## 1.1 研究背景与问题提出

测控技术与仪器专业不仅关注一个传感器能否输出数值，也关注被测对象、采样条件、信号传输、数据处理和结果解释能否组成可信的测量链。在设备远程运维场景中，维护人员可能需要同时回答三个问题：现场现在是什么状态，当前读数是否仍然有效，以及异常出现前后发生了什么。只有视频时，能够看到部分现场现象，却可能无法区分画面冻结和对象静止；只有状态数值时，能够观察量化变化，却缺少连接松动、遮挡和环境变化等视觉背景。

本课题并不假定所有工厂都缺少监控平台，也不把通用摄像头包装成生产线必需设备。研究出发点是一个明确的现有系统缺口：已有树莓派项目能够传输摄像头视频，却尚未围绕设备维护形成状态质量、异常记录和可复核证据。项目最初追求更小的视频延迟，后续曾加入软件模拟往复机构。模拟模型可以验证通信与状态机，但没有实物机构时，往复动作不能证明运动控制性能，且容易使课题的专业价值停留在演示效果。本文将研究对象收敛为真实采集节点的远程诊断，利用已有硬件完成可验证的测控工作流。

这里的“设备”首先指作为边缘观测装置的树莓派、摄像头及其软件采集链路。真实电机、工艺设备或产线是未来接入对象，不属于本文已验证范围。这样的限定使温度、CPU、通信状态等测量量具有实际来源，也使故障实验能够明确控制注入位置，避免把界面上的模型变量当成工业设备测量结果。

## 1.2 需求与已有方案的关系

低成本光电开关适合检测明确位置处的有无、到位或遮挡；编码器和专用传感器能够提供可定量利用的物理量。摄像头的合理职责不是替代这些元件，而是保留空间与环境背景。在本系统中，视频提供诊断上下文，结构化状态负责量化趋势，事件记录将二者按时间关联。因此，即便后续安装光电开关，本课题的观测功能仍可作为辅助层存在，但不得取代必要的保护和联锁。

本系统预设的使用过程是：维护人员打开只读界面，确认节点和视频是否新鲜；出现采集异常时，先区分视频链路与主机状态链路；再检查故障触发前后的温度、负载和通信变化，结合事件图片形成排查依据。本文验证的是这条观测流程能否完成，并不将“减少停机多少分钟”列为实测结论，因为没有真实维修班组和产线对照数据。

## 1.3 相关技术与研究定位

WebRTC DataChannel 为非媒体数据提供基于 SCTP、DTLS 和 UDP 的传输，允许不同可靠性与有序性设置[1]。这为浏览器传输独立 JPEG 图像提供了路径，但使用 DataChannel 不等于使用标准视频媒体轨道，也不会自动获得视频编码器的码率控制。本项目保留该路径，另行研究最新帧 WebSocket 的应用层节奏。WebSocket 是建立于 TCP 的双向协议[2]；应用可以限制发送帧数，却不能因此取消 TCP 的重传和按序交付约束。

信息年龄研究关注接收端持有的信息距其产生时刻有多久[3]。这一视角适合解释本项目中“上一帧传输很快，但屏幕已经很久没有更新”的问题。本文借用该度量定义画面年龄，不将自身工作表述为新的信息年龄理论或最优调度算法。已有研究提供度量背景，本文的工作是将其落实到有真实时间戳和过期状态的浏览器界面。

Linux V4L2 为采集缓冲区提供时间戳及其来源标志[4]，可用于进一步拆分采集与传输段。网络四时间戳方法可估计往返耗时和时钟偏移[5]，但无线不对称和进程调度会影响跨端结果。测量不确定度指南强调测量模型和不确定度来源的明确表达[6]。本文据此区分同端时间差、跨端估计与尚未测得的光学延迟，不把网页中的毫秒数当成完整计量结论。

本课题的贡献属于本科工程设计与实验研究：完成可运行的多源观测系统，形成时间语义一致的事件证据，给出可复算的链路实验，并通过实际系统审计解释哪些优化有依据、哪些没有依据。本文不提出新压缩标准、工业安全等级或人工智能诊断模型。

## 1.4 研究内容与论文结构

本文的研究内容包括需求与边界定义、现有系统审计、采集及通信链路改进、真实状态采样与事件关联、人机界面实现，以及功能与性能验证。第2章说明硬件软件基础和方案选择；第3章建立时间与质量模型；第4章介绍采集通信和 Linux 可靠性改进；第5章说明状态规则、证据存储与界面；第6章给出实验设计、结果及限制；第7章总结结论与后续工作。附录给出部署、复现实验和主要字段，便于答辩时从源代码和原始数据追溯结论。

# 第2章 系统基础与总体设计

## 2.1 现有平台与实测边界

实验平台由树莓派 5、UGREEN USB 摄像头和 Windows 计算机构成。计算机由使用者提供的配置为第12代高性能 i7、64 GB 内存与 RTX 3060；本文不依赖独立显卡推理，也不以此配置代表所有接收端。树莓派通过 Wi-Fi 与浏览器通信，当前没有有线网络对照。摄像头与被摄场景未使用恒定照明、标准图卡和锁定曝光装置，故原生 JPEG 帧大小会随场景变化。

审计发现 Pi 内存空闲较多、未使用交换空间，采集温度约在 60°C 附近波动，初始检查的限频标志为 0。上述结论仅对应检查时刻。更重要的配置发现是内核启动项含 cgroup_disable=memory，容器运行时也报告内存限制不能执行。因此，不能因为服务文件写有 MemoryMax 就认为节点已经具备可靠内存隔离。

## 2.2 架构与职责划分

系统采用采集、传输、状态观测和展示分离的结构。C++ 采集进程从 V4L2 获取原生 JPEG，发布到共享内存；视频网关或 Node 最新帧服务读取当前完整帧。独立 Python 观察服务读取同一发布时间和 Linux 状态，不需要接管摄像头，也不需要通过视频会话才能提供状态。浏览器通过 Node 提供的只读代理获取状态，并在独立视频区域展示当前画面。

该分离具有实际故障定位意义。暂停采集进程时，视频应停止，但观察服务仍可报告主机状态与过期的采集时间。阻断浏览器的状态请求时，视频可以继续，页面应明确标记状态不可用，而不是使全部数值假装正常。需要强调的是，这些通道仍共享同一树莓派、无线链路和前端服务；系统并无硬件冗余，不能保证主机掉电后仍能远程诊断。

## 2.3 方案比较与选择

早期项目曾探索 YUYV、DCT 与 LZ4 的变化域传输。该历史探索保留在独立目录，用于解释设计过程，不作为当前运行链路。当前摄像头已经直接提供 MJPEG，再在 Pi 上解码和重编码会增加处理步骤；因此本课题优先复用原生压缩帧，将研究资源集中于有界排队、时间可观测性和故障关联。

这并不表示 MJPEG 天然优于 H.264 或 H.265。帧内独立 JPEG 易于按最新帧丢弃，代价是带宽通常较大；经低延迟配置的帧间编码也可以用于交互场景，但需要公平的编码参数和硬件条件对照。本文没有完成这样的对照，不能写成“证明 H.264 延迟必然较高”。同样，WebSocket 在当前无线环境中的效果不等于所有网络中都优于 WebRTC。

表2-2 方案功能与约束

| 方案 | 本项目的作用 | 主要约束 |
| --- | --- | --- |
| WebRTC DataChannel | 保留原有 JPEG 分片路线 | 分片完整性、会话恢复和拥塞行为需管理 |
| 最新帧 WebSocket | 主观测页默认视频路线 | TCP 仍有重传和队头等待 |
| 独立时钟 WebSocket | 降低校准与大图像消息直接串行的耦合 | 仍共享无线队列，不是硬件同步 |

| AI 实时视觉分析 | 本轮不采用 | 尚无任务、标签和准确率验证依据 |

## 2.4 安全与应用范围

新观察接口只读，Python 服务绑定回环地址，Node 只代理白名单路径。系统没有通过网页开放电机启动、速度设定或紧急停止。因此，本课题不涉及实际运动控制的闭环稳定性证明，也不能将视频低延迟等同于远程控制安全。未来如接入电机或 PLC，保护、互锁、看门狗和失联处理必须独立在设备侧实现。

当前原型在可信局域网内使用，浏览器入口尚未配置身份认证和 HTTPS。现场图像具有隐私属性，即使接口只读也可能泄露环境信息。本文不将服务权限收紧等同于完整网络安全方案。公网使用、工厂 OT 网络接入和多用户访问需要额外的认证、审计、网络分区、证书与权限设计，这些属于明确的未完成事项。

# 第3章 时间测量与数据质量模型

## 3.1 测量量与时间边界

视频链路的“延迟”必须先定义起止点。本文记录驱动时间、出队时间、共享内存发布时间、服务发送调用时间、浏览器收到完整消息时间和解码完成时间。Pi 侧使用单调时钟，浏览器使用 performance.now。UTC 仅用于事件的人类可读时间和实验日期，不直接用于毫秒级跨端相减，以避免系统时钟调整破坏持续时间计算。

表3-1 时间戳与时钟域

| 符号 | 事件 | 时钟域 |
| --- | --- | --- |
| t_drv | V4L2 缓冲时间戳 | 驱动声明的 Pi 单调时钟 |
| t_dq | VIDIOC_DQBUF 完成 | Pi 单调时钟 |
| t_pub | 完整 JPEG 发布 | Pi 单调时钟 |
| t_send | 调用发送函数前 | Pi 单调时钟 |
| t_recv | 浏览器整帧消息回调 | 浏览器单调时钟 |
| t_dec | JPEG 解码完成 | 浏览器单调时钟 |
| theta | Pi 时钟减浏览器时钟 | 网络探测估计 |

驱动时间戳只在声明为单调时钟且不晚于出队时间时使用。本设备实际报告的时间来源包含 SOE 标记。依据接口定义，SOE 和 EOF 表示不同的采样时间来源[4]，但本课题没有用示波器、发光器件或高速相机校验驱动标记是否精确对应光学曝光。因此，t_drv 仍被视为驱动提供的时间锚点，而不是经外部校准的真实曝光时刻。

## 3.2 四时间戳与分段估计

一次探测包含浏览器发送时刻 c1、Pi 接收时刻 p2、Pi 回复时刻 p3 和浏览器接收时刻 c4。若一次交换内时钟速率近似相同，扣除服务端处理时间后可得到网络与调度往返量 r；在近似对称假设下得到时钟偏移估计 theta。该结构参考网络时间同步中四时间戳思想[5]，但本项目没有实现完整 NTP 协议，也不会调整系统时间。

同端的采集段和解码段不需要跨端偏移。发送至接收段则包括应用及内核排队、TCP 或 SCTP 行为、无线传输以及浏览器回调调度，不能命名为纯空口耗时。旧 published_ms 为毫秒整数，VPF3 的精确字段为微秒，因此整帧旧口径与分段和之间可能存在不足 1 ms 的取整差异。

发布至解码估计反映数据被本地发布后的交付；驱动至解码估计更靠近采集起点，但仍不包含显示器扫描、像素响应和人眼观察。本文始终不将这两个数值改称为玻璃到玻璃实测。不同文献若起止点不同，即便都写“延迟”，也不宜直接比较数字大小。

## 3.3 画面年龄与状态新鲜度

已完成帧的时延是一个历史样本。画面冻结后，该帧的交付时延可以仍然很小，却不能代表屏幕当前内容新鲜。本文定义画面年龄为当前浏览器时刻映射到 Pi 时钟后，与最近显示帧发布时间的差值。只要没有新帧替换，它就应随时间增长，而不是保持最后一次成功值。

{{EQ_AGE}}

状态服务也保存采样时间和运行批次标识 run_id。浏览器不能把一次有效响应无限期保持为在线，而应根据响应携带的年龄及本地等待时间判断是否过期。观察服务将超过 2.5 s 未更新的状态判为 STALE；完全没有样本为 OFFLINE。正常数值为零、传感器不可用和通信中断是不同状态，应在数据结构和显示上区分。

界面中的“采样时帧年龄”指观察服务读取共享内存时看到的年龄。由于它仅按 1 Hz 更新，不能把该时间戳外推为摄像头此刻没有继续发布。否则一个健康的 30 fps 摄像头也会在两次状态采样之间被错误显示为逐渐过期。当前实时画面年龄来自视频链路自身，状态采样年龄单独显示，二者具有不同含义。

## 3.4 不确定度来源与报告规则

测量模型中的不确定性主要来自网络双向不对称、时钟相对漂移、时间戳取整、驱动时间来源可信度、浏览器回调调度和解码后显示过程。项目采用 r_min/2 加 1 ms 作为保守提示量，其中 1 ms 用于提示旧发布时间量化，但并没有完成标准器校准、各分量统计建模或合成扩展不确定度。按计量术语，这不是符合完整 GUM 流程的测量不确定度报告[6]。

对跨端估计出现负值时，界面不将其钳位成好看的 0 ms，而是标记估计无效或不显示该值。实验文件保留相关计数，以免选择性删除不利样本。对解码失败和未完整到达的帧，单纯的成功帧延迟分布不会反映其等待代价，因此同时记录帧间隔、超过 200 ms 与 1 s 的间隔次数、年龄分布和失效采样数量。

分位数使用排序后的最近秩法，P95 取第 ceil(0.95n) 个样本，不使用可产生不同结果的插值默认值。连续视频帧具有明显时间相关性，因此本文不把几千帧机械视为几千个独立重复实验，也不据此给出过于狭窄的独立同分布置信区间。轮次之间的可重复性比单轮样本数量更值得关注。

## 3.5 事件与图像关联模型

事件触发时间和图像发布时间均来自同一 Pi 单调时钟，关联差值定义为事件采样时刻减去快照发布时间。快照是在规则触发后读取的，此时新图像可能刚发布，因此差值可以为负。负差值不必然是错误，而说明图片稍晚于事件采样点；正差值较大则说明图片可能已经陈旧。系统同时保留图片质量和时间差，避免把两者仅凭同一页面位置误称为严格同步。

{{EQ_CORRELATION}}

一次事件关联最多十个之前状态样本和五个之后样本，启动后不足十个样本时如实保存已有数量。进程关闭或采样异常时，后续上下文可能不完整，记录 context_complete=false。图片 SHA256 用于识别保存对象和检查内容一致性，不证明相机来源可信，也不是数字签名。以上字段构成可解释的实验记录，而不是具有司法取证效力的证据链。

# 第4章 采集通信与系统可靠性改进

## 4.1 原生帧采集与一致性读取

采集程序使用 V4L2 mmap 方式管理缓冲区，从摄像头读取已压缩 MJPEG。有效载荷由 bytesused 决定，而不是将固定大小缓冲区全部作为图像。程序取得最新有效帧后，将图像与头部元数据发布到共享内存。当前布局保持原有 48 字节头和 JPEG 起始位置，在 128 MiB 共享空间末尾增加 64 字节计时扩展区，兼容旧网关。

写入过程采用奇偶序号标志：写入期间标记未完成，提交后为完成状态。读取方先读取头部，再取图像与扩展区，最后重读并比较头部；若序号为奇数、前后头不一致、长度越界或时间戳不合法，则拒绝该快照。此处的目标是避免读到混合帧，而不是补齐所有被覆盖的帧。摄像头继续写入时，宁可跳过一次不完整读取，也不向浏览器发送伪完整 JPEG。

文件名相同不意味着共享内存对象始终相同。采集服务重新创建文件后，原文件描述符可能仍指向旧 inode，导致接收方持续读到历史内容。新版本定期比较路径对象身份，并在替换或消失时关闭旧句柄、重新打开。Python 低频观察服务每次按名称读取，避免长期固定旧对象。相关测试包含文件替换、延迟创建、写入中状态和头部复核失败。

上述方案仍不是通用的跨平台共享内存一致性证明。它基于目前的 Linux 文件映射、现有发布协议和实际测试。若未来改变写入端结构、处理器体系或内存同步方式，需要重新审核发布顺序与内存可见性；不能仅因单次浏览器能显示图像就认为所有并发情况已经验证。

## 4.2 最新帧拉取与有界排队

最新帧 WebSocket 将浏览器看作具有有限接收能力的消费者。默认策略只允许一个未确认帧：浏览器解码完成后归还额度，服务端再读取当前共享内存，而不是依次发送期间错过的历史帧。浏览器侧最多保留一个正在解码的帧与一个待解码最新帧；新帧替换等待帧时归还其额度。重复确认和伪造确认不会扩大窗口。

该设计将“保证每一帧送达”改为“尽量展示新状态”，适合只读观测，不适合要求完整帧序列的视觉计量或追溯录像。不能简单将两者混为同一种质量目标。如果后续需要缺陷检测，必须另行记录有效采样率与丢帧影响，或者将分析链路与交互预览分开。

项目还保留收到整帧后归还额度的 receive 策略，以及最多两帧未确认的 window2 策略。前者允许网络与解码部分重叠，后者增加并行度，但都可能扩大旧数据等待。已有六轮发送节奏实验表明，扩大窗口没有稳定改善时延尾部，因此默认仍采用 decode。该决策由实际数据支持，而不是假定“流水线越深越快”。

应用层窗口不等于端到端时限。已经进入 TCP 缓冲的 JPEG 不能被应用选择性撤回；无线重传或断续连接仍能造成长尾。因此，本系统用有界应用排队降低可控部分的积压，用新鲜度标记暴露不可控部分，而不承诺任何条件下均低于某个毫秒阈值。

## 4.3 独立时钟通道

若校准消息与 JPEG 共用一条有序连接，时钟回复可能排在大图像后面，其往返量同时受到应用消息串行影响。新版本增加 role=clock 的独立 WebSocket，只传输短时钟请求与响应，使用与视频服务相同的 Pi 单调时钟。它不占用单 viewer 位置，断开后可独立重连，且消息大小、请求速率和待发送量具有上限。

独立连接的意义首先是测量结构更清楚，而不是保证视频本身更快。它仍与视频竞争同一 Wi-Fi，无线和内核拥塞可能同时影响两条连接；最小往返样本的变化也可能仅改变偏移估计，进而改变报告时延，而并未改变物理交付过程。因此对照实验同时比较视频帧率、年龄、间隔和时钟 RTT，不能用一个变小的“延迟均值”单独证明优化成功。

时钟请求编号在视频重连时继续递增，避免旧连接迟到回复恰好匹配新探测编号。对于非法类型、二进制时钟消息、超限频率和超大内容，服务关闭该连接；没有把独立时钟扩展成任意命令通道。其主要目标是降低链路耦合并提高测量可解释性。

## 4.4 Linux 审计与优化取舍

本轮先检查真实配置，再决定是否修改。CPUFreq performance 策略会请求策略允许的高性能频率，但频率仍可能受到硬件与温度约束[7]。当前 Pi 已使用该策略，Wi-Fi 省电也已关闭，因此重复设置不能作为新增性能成果。CPU 隔离、采集和网关亲和性原本已经存在；在总负载较低且缺少可重复受控数据时，没有继续盲目改变 IRQ 或实时调度优先级。

网络端检查到 fq_codel 已启用，但该时刻软件队列没有积压。qdisc 统计不覆盖无线固件内部和接入点缓冲，零丢包不能证明整条无线链路没有等待。本文没有因一个工具显示零队列，就排除网络问题；也没有未经验证地替换拥塞控制或降低 MTU。后续若进行网络参数实验，应一次只改变一个因素，并记录恢复值。

本轮落实的系统级措施包括：将每 30 帧一次的普通采集日志降低为每 300 帧一次，减少正常状态下的日志工作；增加退出信号处理和连续五次采集等待超时后的非零退出，由现有进程监督器接管恢复；为信令和观察服务增加文件系统只读及禁止提权等约束[8]。这些改进提高可维护性和故障响应，不应写成已经量化降低多少毫秒的性能提升。

关键配置保留回退路径，包括原信令目录、服务单元、采集源码及旧 Docker 镜像。没有为了追求漂亮结果更改 Wi-Fi 连接、路由、SSH 或内核启动参数，也未重启整机。发现 memory cgroup 不可用后，界面明确显示这一限制，而没有用配置文件中的名义限额掩盖实际内核能力。

## 4.5 接口鲁棒性与服务边界

信令 HTTP 服务现在捕获 URL 解码异常，返回 400 而不是让非法百分号编码触发未捕获异常。静态文件访问使用规范化路径和目录包含关系检查，拒绝越界路径、NUL 与异常分隔符。只读观察代理仅允许明确的 GET 路径，并设置响应大小和超时约束，不能被当成任意地址转发器。

网关角色限制为回环来源，避免局域网普通浏览器伪装为本机视频网关覆盖会话。原系统仍为单 viewer 设计，同时打开多个视频页面会互相替换；这不是多用户监控平台。新界面中的“独立视频”在同一页导航，避免主动制造两个互抢的观察窗口。完整的连接总数限制、认证及拒绝服务防护仍需在生产化阶段补充。

# 第5章 状态采样与事件证据实现

## 5.1 真实状态采样

观察服务每秒读取 Linux CPU 计数、内存信息、网络接口计数和 SoC 温度。CPU 利用率由相邻采样的累计计数差计算，首次采样没有前值时返回空。网络速率同样由字节差和时间差换算，计数器回退或时间异常时不输出负速率。内存可用量、温度或信号读不到时保留缺失状态，不用默认零值掩盖读取失败。

SoC 温度是内置传感器输出，不是被维护电机的绕组温度。Wi-Fi 信号值是驱动报告的接收信号指示，不能直接换算为丢包率或通信质量等级。接口字节率包含其他网络活动，不是纯视频码率。对每个量保留其来源和单位，可以防止界面从“主机观测”不知不觉滑向“设备工艺测量”的过度解释。

观察循环使用单调时间安排下一次采样，并记录采样开始相对计划的迟到量。若一次操作超过周期，不连续追赶补写虚假样本，而是从后续时间继续安排。采样异常时保留最后值但标为过期，避免把缺测区间用插值伪装为真实观测。趋势图也不跨越运行批次和明显缺口连接曲线。

## 5.2 告警状态机与回差

规则引擎将异常条件与事件记录分离。每次采样评价条件，但只有状态由未触发变为触发、或由触发变为恢复时才生成事件，避免相同异常每秒重复刷屏。触发要求连续满足若干次，恢复要求连续两次正常。温度、CPU 和信号规则具有回差，以降低阈值附近往返变化造成的抖动。

表5-1 诊断规则参数

| 规则 | 触发判据 | 触发次数 | 恢复判据 |
| --- | --- | --- | --- |
| 采集过期 | 采集质量不是 GOOD | 2 | 连续 2 次 GOOD |
| 主机高温 | 温度不低于 75°C | 3 | 连续 2 次低于 70°C |
| 主机高负载 | CPU 不低于 90% | 5 | 连续 2 次低于 75% |
| 无线弱信号 | 信号不高于 -70 dBm | 5 | 连续 2 次高于 -65 dBm |

这些阈值由实验需求设置，不是制造商给出的安全保护值。只有采集停止规则进行了本轮真实故障注入，其余规则通过软件测试验证逻辑，没有用加热或破坏网络的方式进行硬件极限试验。故不能由单元测试推断高温保护可靠性，也不能将弱信号规则称为无线故障分类器。

采集质量超过 500 ms 为过期；在 1 s 采样和两次去抖下，从最后一帧到告警之间存在采样相位差。若发布恰好停在某个采样点后，第一次明确异常可能等到下一次采样，第二次异常再确认。理论估计与实测时间应在这一采样机制下解释，而不是要求所有轮次精确等于两秒。暂停确认的时刻也不必等于最后一帧发布时刻。

## 5.3 事件保存与容量控制

SQLite 保存状态序列和事件，图像以二进制字段留在本机。采用 WAL 模式以支持当前轻量读取与写入工作流；WAL 的检查点与文件生命周期仍需管理[9]。系统按记录数保留状态和事件，图片另设数量及总字节上限。较早图片可以删除而事件元数据继续存在，查询时用 image_available 区分“没有保留图片”与“HTTP 请求错误”。

当前逻辑保留最多约 86400 条状态样本，清理每 60 次写入执行；事件最多 500 条，图片最多最新 20 张且总负载不超过 64 MiB。这是逻辑数据保留策略，不能理解为数据库文件的硬配额。SQLite 空闲页、事件 JSON 和 WAL 仍会占用磁盘，长期运行应增加磁盘剩余量检查、归档或容量告警，本次短时试验尚不能替代长期增长验证。

故障快照不是持续录像。若采集停止，触发事件可能只能保存停止前的最后一帧，此时质量为 STALE，时间差明确为较大正值。恢复事件的图像可能较新。将两张图片及其时间语义一起展示，比单纯输出一个“故障截图”更准确，也能提醒维护人员不要误把旧图当成故障瞬间的现场。

## 5.4 人机界面与操作流程

主界面采用实时监测和事件记录两个视图。顶部显示画面年龄、驱动至解码估计、采样时帧年龄、主机温度、CPU 及活动告警数；中央展示原视频；侧栏展示状态质量、信号、吞吐、内存与采样调度情况；下方为最近五分钟趋势和事件。数值始终附有单位，未知值为空，过期数据与在线状态采用不同标识。

事件视图可筛选触发或恢复，查看规则、来源、单调时间关联差、前后样本数量和上下文完整性，并导出 JSON。维护流程不要求操作人员手动在不同程序中对齐时间。原视频入口仍保留，便于单独测试通信；同时说明单 viewer 限制，不把当前原型包装成多席位生产监控系统。

界面以真实摄像头图像为视觉内容，没有另造一个虚拟设备运动场景。公开仓库和论文不发布家庭环境快照，仅保存数值证据、架构图和统计图。浏览器自动检查包括桌面、平板、390 px 与 320 px 宽度，验证没有水平溢出和主要数值裁切；Canvas 像素检查验证图像不是空白。该检查证明测试视口下的功能和布局，不证明所有浏览器和显示设备都兼容。

## 5.5 面向制造业岗位的工程能力

本课题与测控专业的联系落在测量链定义、采样与新鲜度、状态判断、故障复现、数据留存和结果解释，而不是单纯套用“工业互联网”名称。对设备维护和自动化岗位而言，可展示的成果是从现象追溯到采集、主机和通信的排查步骤，以及能让他人复现实验的记录。对工艺或制造工程岗位，系统可以作为观察工序和记录异常的基础，但尚未完成节拍优化或工艺能力分析。

毕业设计不能替代实际电气识图、PLC 调试、仪器使用和现场安全训练。本文也不以一个网络项目证明已具备生产设备维修资质。合理的后续路径是在借到设备或进入实习场所后，增加一个经过标定、单位明确的真实物理量，以此验证视频和状态关联对排查的帮助，再考虑更复杂的协议或算法。

# 第6章 实验设计与结果分析

## 6.1 验证分层与数据质量

实验分为软件回归、浏览器功能、采集故障注入和通信性能四层。回归测试用于检查边界输入和状态机；浏览器测试验证真实图像、布局、过期提示与导出；故障注入验证真实进程暂停后是否形成证据；通信实验衡量当前无线环境下的交付表现。不同层次的通过结果不能互相替代，例如单元测试通过不等于无线链路达到确定性时延。

原始文件记录实验开始时间、有效持续时间、图像尺寸、每帧时间戳、时钟样本和每秒状态响应。它们不包含 JPEG 图像和登录凭据。汇总脚本从原始数据重算均值与最近秩分位数。统计中保留失败状态请求、负时延计数和未取得有效年龄的样本数量，防止只报告成功结果。

实验不是封闭射频环境：Pi 与 PC 都通过 Wi-Fi 连接，场景和照明未锁定，电脑同期执行了本地文档编辑，部分轮次进行了低频 Ping 和只读审计。本文对这些干扰据实记录。顺序对照可以揭示当前条件下的趋势，却不能将全部差值归因于一个软件开关。

## 6.2 回归与页面验证

Node 侧 45 项测试通过，覆盖旧协议解析、有界重组、额度限制、最新帧读取、时钟失效、独立时钟、路径边界和只读代理；Python 观察模块 9 项测试通过，覆盖计数器差分、缺测处理、共享内存质量、告警回差、记录保留、只读接口与后续上下文。上述新测试在开发机和树莓派环境均运行通过。原模拟工位不属于本文实验对象，其历史测试不与新监测测试混算。

浏览器验证读取真实摄像头 JPEG，检查尺寸为 1280×720 且像素非空。分别阻断状态接口和暂停浏览器视频请求时，界面能独立显示状态通道离线与画面过期。恢复请求后数据继续更新。事件视图可读取六条采集暂停／恢复记录，导出结构包含 MEASURED 来源，未发生浏览器脚本异常。

## 6.7 Linux 发送平滑探索

为检验无线固件之前的突发发送是否值得进一步处理，增加了原 fq_codel、fq 每流最大 40 Mbit/s、恢复 fq_codel 的三轮顺序探索。fq 提供按流调度与 pacing，最大速率参数限制的是流，而不是整个接口的总带宽[10]。每轮保持同样的独立时钟、decode 与 720p，计划测量 120 s。修改前设置 240 s 自动恢复任务，实验后主动恢复原队列并停止临时定时器，没有写入永久启动配置。

## 6.8 误差与局限讨论

第一，本文没有光学基准。跨端时钟估计对网络不对称敏感，驱动时间戳的 SOE 声明也没有被外部仪器验证。所有驱动至解码数值应保留“估计”字样。第二，成功帧统计存在幸存样本问题；停顿末尾没有下一帧时，相邻解码间隔还未闭合，故最大间隔可能低于实际未更新时长，年龄曲线和校准失效数量应一并检查。

第三，无线条件变化显著。此前一组短时实验没有秒级间隔，不意味着后续任何时段都不会出现。长尾期间 PC 到 Pi 的 90 次 Ping 有 10 次未在 1 s 内返回；随后近同时的路由器探测中，PC 平均约 2 ms、最大 20 ms，Pi 平均 92.776 ms、最大 930.229 ms，均收到 90 次回复。这将排查优先级指向 Pi 与接入点一侧及其交互，但没有有线对照、同步逐包记录和空口捕获，不能强行把责任归给某个驱动。

第四，采样规则只验证了部分异常。CPU、温度与信号诊断是阈值提示，不是故障因果模型；没有真实维修标签，不能报告准确率、召回率和节省工时。第五，短时间运行与逻辑容量限制不等于长期可靠性，存储增长、断电一致性和多用户访问仍需更长验证。

第六，系统对象是观测节点，而非生产设备。论文不包含编码器精度、调速误差、机械定位精度或工艺能力指数，也不通过虚拟变量补齐这些指标。实物接口一旦加入，应重新建立量程、标定、采样同步与安全边界，而不是直接复用主机温度阈值。

# 第7章 结论与展望

## 7.1 主要结论

本文在已有树莓派视频链路上完成了一个只读远程观测原型，使项目从单一视频传输扩展为视频、真实主机状态和故障证据的协同展示。通过明确时间戳语义、独立新鲜度状态和事件上下文，系统能够区分历史帧的交付时延与当前画面的陈旧程度，并对采集停止形成可复核的触发和恢复记录。

工程实现保留了原生 720p MJPEG 质量、旧 WebRTC 入口和最新帧 WebSocket，新增独立状态与时钟通道，修复 URL 异常和共享内存替换恢复问题，并增加进程退出监督与权限约束。三轮真实采集暂停验证了状态通道持续工作及证据保存流程，软件与浏览器验证支持本次交付功能的正确性。

性能实验同时表明，应用层有界队列和独立时钟不能消除共享 Wi-Fi 的长尾。本文未达到任何条件下稳定超低延迟的目标，也没有将正常帧统计包装为确定性实时保证。这样的结论为后续工作给出清楚方向：优先验证网络和实际采集时序，而不是继续盲目压缩已很短的用户态复制时间。

## 7.2 后续研究顺序

第一步应在相同图像与光照条件下取得有线基准或独立接入点对照，再按单一变量研究无线信道、后台扫描、接入点负载与发送方式。若仍只能使用当前 Wi-Fi，应延长观测、记录网络事件和节点两端 RTT，避免通过高风险修改网络配置使唯一远程通道失联。

第二步是补充光学端到端测量。可在具备现场配合时使用可见计时基准、受控 LED 或高速相机，定义曝光起点和显示终点，再与驱动时间戳估计比较。只有获得参考测量后，才能讨论偏差、重复性和更完整的不确定度预算。

第三步是接入一个真实、低风险且有单位的物理量，例如借用仪器输出的温度或转速读数。必须先明确量程、校准和接口隔离，再将状态适配到现有事件结构。若涉及电机，设备侧独立保护优先于远程操控，观察网页不能作为急停或安全联锁。

第四步是可选的离线 AI 辅助。事件前后状态和图像已经形成可索引数据，未来可用于事件摘要、检索相似记录和提出待验证排查假设。AI 不放入关键视频交付路径，不直接生成设备动作，也不在没有标签和评价集时宣称智能诊断有效。这样既保留拓展价值，又不让模型推理侵占本课题最需要验证的测量和可靠性工作。

## 7.3 毕业设计成果与适用性

本课题可提交的成果包括部署的软件、只读 HMI、故障实验脚本、原始数值文件、可复算统计、审计与回退记录以及本文。它适合展示测控系统集成、Linux 排查、接口契约、测量边界和实验论证能力。制造业实际应用价值仍需通过接入真实对象、现场人员使用和对照验证来建立，不能用毕业设计题目本身替代这些证据。
