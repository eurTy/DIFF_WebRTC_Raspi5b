# 工业执行机构远程测试与故障诊断方案

更新：2026-10-10。状态：**设计方案，尚未实现工业控制功能**。现有真实能力是摄像头采集、视频传输、实时延迟估计及链路测试；没有接入电机、限位、电流传感器或 PLC。

## 1. 题目与需求

建议毕业设计题目：**面向工业执行机构的状态监测与远程测试系统设计**。完成真实故障验证后，再考虑在题目中加入“故障诊断”。

对象限定为一个往复动作单元，例如送料推杆、定位挡板或夹紧机构，不做小车，不同时铺开整条产线。第一阶段建立软件模拟工位，不宣称模拟工位等于真实机械设备。

要解决的具体问题：设备偶发“动作超时/不到位”后，仅看报警代码难以重现当时的指令和动作过程；远程维护人员需要把命令、输入反馈、动作耗时和现场视频放在同一个时间轴上，区分通信异常、限位反馈异常与疑似机构异常，并形成可复查的测试记录。

这是一项待验证的维护需求，不是已经完成工厂调研的结论。后续应向设备老师或企业维护人员核实：常见故障、现有报警日志缺什么、允许记录什么画面、希望怎样导出报告。

**相较单一视频项目的增量**：有被测对象、有状态量、有动作约束、有测量误差说明、有故障注入、有验收报告。低延迟视频变成测试工具中的一项能力。

## 2. 摄像头和现有仓库的作用

| 现有模块 | 工业方案中的用途 | 不能代替什么 |
| --- | --- | --- |
| V4L2 原生 MJPEG 采集 | 观察机构动作、松动、遮挡和人工干预 | 不能代替独立限位或安全装置 |
| 最新帧共享内存和有界发送 | 减少维护画面显示历史动作的风险 | 不能保证 Wi-Fi 永不中断 |
| WebRTC / WebSocket 对照 | 比较同画质下的延迟、更新率和中断恢复 | 不能证明某协议适用于所有工业现场 |
| 驱动/发送/解码计时 | 评估视频证据与状态事件的时间偏差 | 不是完整光学测量，也不是精密时间同步 |
| 浏览器界面 | 改造成设备测试 HMI：状态、命令、报警、曲线、视频 | 不是 PLC 或安全控制器 |
| 延迟与重连测试 | 扩展为通信故障和设备测试用例 | 不能替代现场验收 |

摄像头负责现场证据，限位/电流等信号负责状态判断；不做 AI 读仪表，不让视频识别进入动作闭环。未来 AI 仅可离线整理测试记录、提出排查候选，由人确认，且不是论文成立的前提。

## 3. 架构与控制边界

```text
PC 软件模拟工位（第一阶段，Modbus TCP server）
  状态机 + 模拟限位 + 故障注入 + 确定性测试时钟
       | Modbus TCP
       v
Pi 设备网关（后续新增独立服务）
  轮询/命令校验/时间戳/通信状态/事件存储
       | 独立的状态与命令连接
       v
PC 浏览器测试 HMI <--- 现有独立视频通道 <--- Pi + 真实摄像头

后续替换：PC 模拟工位 -> 真实 PLC / 隔离 I/O / 执行机构
```

第一阶段模拟服务放 PC，不在视频采集进程内加控制逻辑。选用成熟的 PyModbus 客户端/服务端能力，锁定安装时核验过的版本，不自行实现 Modbus 编解码。Modbus 的寄存器语义由本项目定义，换真实 PLC 时需要映射，不是通用即插即用接口。[Modbus 官方介绍](https://www.modbus.org/introduction-to-modbus)、[PyModbus 官方项目](https://github.com/pymodbus-dev/pymodbus)

状态/命令服务采用独立进程、独立连接和有界队列，避免视频解码或大帧发送阻塞其应用事件循环。但两路仍共享 Wi-Fi，不能称为“确定性实时控制”。

动作状态机、互锁和通信超时处理必须在被控端执行。浏览器断开不能让已排队的动作在重连后自动补发。真实设备的停机方式由风险评估决定，不能简单假定所有执行器断电都安全；气动夹具还可能涉及保持夹紧等要求。软件停止按钮不是急停，真实设备需要合适的本地硬件保护。

当前视频服务仅适合可信局域网。增加实际控制前必须实现登录鉴权、只读/操作角色、单一控制权、命令审计；外网接入需安全网关/VPN及 TLS，不能把现有端口直接映射公网。

## 4. 最小功能与接口草案

### 状态与命令

状态机：`OFFLINE -> IDLE -> EXTENDING -> EXTENDED -> RETRACTING -> IDLE`；运行异常转 `FAULT`。模式为 `MANUAL` / `AUTO`，动作中拒绝切换。手动动作也必须经过同样互锁。

每条命令包含 `command_id`、动作、操作者、有效期和来源。被控端返回 `ACCEPTED / COMPLETED / REJECTED / FAILED`，接收成功不代表动作完成。同一 ID 重复请求只返回既有结果；超时后先查询状态，不盲目重发运动命令。故障复位仅清除已满足复位条件的锁存报警，不自动启动。

建议初始轮询周期 50 ms，3 次连续失败标记通信异常，最终阈值经实验调整；这只是软件验证参数，不是现场安全规范。界面区分 `GOOD / STALE / OFFLINE / SIMULATED`，离线时保留最后读数但明确标记过期，不能显示为当前正常状态。

### 模拟寄存器草案

以下使用 **PDU 零基地址**，不是 40001 风格展示地址；均为 Holding Register。32 位值占两个寄存器，高字在前。发布实现前冻结协议版本与读写权限。命令块须一次写入并经序号确认，避免分次写入产生混合命令。

| 地址 | 数量 | 名称 | 方向/含义 |
| ---: | ---: | --- | --- |
| 0 | 1 | protocol_version | 只读，初始 1 |
| 1 | 1 | state | 只读，状态机枚举 |
| 2 | 1 | mode | 只读，实际模式 |
| 3 | 1 | input_bits | 只读，原点/伸出限位/本地许可 |
| 4 | 1 | output_bits | 只读，伸出/回退输出状态 |
| 5 | 1 | alarm_code | 只读，锁存报警 |
| 6 | 2 | cycle_count | 只读，完成往复循环数 |
| 8 | 2 | last_action_ms | 只读，被控端单调时钟测得的动作耗时 |
| 10 | 1 | current_mA | 只读，第一阶段只能是模拟值；无数据时质量标志无效 |
| 11 | 1 | quality_bits | 只读，模拟/输入有效/电流有效 |
| 12 | 2 | heartbeat | 只读，单调计数，不用 UTC 代替 |
| 14 | 2 | status_sequence | 只读，状态快照版本，用于检测撕裂/重复采样 |
| 100 | 1 | requested_action | 写入命令块，伸出/回退/停止/复位/模式切换 |
| 101 | 2 | command_sequence | 写入命令块，对应网关命令 ID 的会话内序号 |
| 103 | 1 | command_parameter | 写入命令块，例如目标模式 |
| 104 | 1 | validity_ms | 写入命令块，接收后的有效时间窗口 |
| 110 | 2 | acknowledged_sequence | 只读，最近确认序号 |
| 112 | 1 | command_result | 只读，接收/完成/拒绝/失败 |

序号和有效期不能单独防止跨连接重放：实现时还需网关会话世代、断线清队列、被控端重启识别及重新授予控制权。真实执行器接入前必须通过相关测试。

### 报警规则

| 现象 | 可以给出的结论 | 限制 |
| --- | --- | --- |
| 伸出/回退超时且目标限位未到 | 动作超时，检查执行机构及反馈链路 | 没有额外证据不能直接判为机械卡滞 |
| 两端限位同时有效 | 输入组合矛盾，检查接线/开关/逻辑 | 第一阶段是注入故障，不是实物检测 |
| 动作结束后原限位不释放 | 限位异常或机构未离开 | 需结合动作、电流及人工查看 |
| 心跳/轮询过期 | 设备通信异常，数据过期 | 不能据此认定电机故障 |
| 视频年龄超阈值 | 视频不新鲜，不宜凭画面判断当前动作 | 不等于被控端失联 |
| 电流异常且动作超时（以后） | 疑似堵转/过载，需验证 | 阈值需标定，不能只用通用固定值 |

### 记录与量化

保存 `run_id`、命令 ID、状态序号、单调时间、UTC、来源设备、数据质量、配置版本、报警、视频帧 ID、视频发布时间和时钟误差估计。单设备动作耗时采用同一单调时钟相减；跨设备对齐同时保留校准不确定度。建议 SQLite 保存结构化事件，按测试运行导出 CSV/JSON 与 HTML 报告。

核心指标：动作耗时均值/P95/标准差、100 次循环完成率、命令确认延迟、报警检测延迟、断线恢复时间、视频年龄/P95、最大更新间隔。报告同时列出失败与超时，不能只统计成功动作。

50 ms 轮询存在采样量化和网络等待，网关收到限位变化的时间不等于开关真实触发时间。暂不报告毫米级位置精度或电流测量准确度。物理阶段需另做传感器标定、重复性和不确定度分析。

视频证据先做带帧时间戳的报警快照；前后若干秒缓存录像作为第二阶段能力，需独立有界缓存/异步存储，测量开启前后的 CPU、磁盘和延迟影响。先确定录像权限和保留期限，不在公共 GitHub 放现场画面或凭据。

## 5. 验收与演示

模拟验收目标是待实现的测试要求，不是当前实测结果：

| 用例 | 操作 | 验收要求 |
| --- | --- | --- |
| 正常往复 | 运行 100 个模拟循环 | 每个命令和动作结果可关联；无未解释丢失记录 |
| 双向互锁 | 伸出中请求回退 | 按冻结的状态机规则拒绝；不能双输出同时有效 |
| 限位故障 | 注入限位卡住/双限位 | 对应报警、时间和输入组合均被保存 |
| 动作超时 | 延长模拟动作到超时阈值以上 | 被控端本地进入规定故障状态，HMI 显示具体原因 |
| 重复命令 | 同一 ID 连续发 10 次 | 最多执行一次，重复返回同一结果 |
| 断线与重连 | 中断网关到模拟设备连接 | 过期标记生效；不补执行断线前遗留动作 |
| 视频暂停 | 单独暂停视频收帧 | 视频年龄增长；设备状态服务仍可用 |
| 网关重启 | 命令执行期间重启网关 | 恢复后先核对设备状态，不自动重新启动 |
| 权限隔离 | 只读用户提交动作 | 拒绝且审计记录完整 |
| 报告复核 | 导出一次完整测试 | 由原始记录重算指标，与界面汇总一致 |

约 6 分钟演示流程：

1. 打开 HMI，展示连接、模式、限位、视频和当前测试编号；明确标注模拟工位。真实摄像头画面只证明视频链路，不能伪装成模拟机构的实拍。
2. 发起一次正常往复，查看命令接收、伸出到位、回退到位的顺序和耗时曲线。
3. 注入“伸出限位不触发”，观察本地超时、报警、事件时间轴与视频快照关联。
4. 重复发送同一命令并模拟断线，证明不会重复动作或在恢复后自动启动。
5. 单独暂停视频，展示视频过期和设备离线是两类状态。
6. 导出测试报告，展示正常/异常对照、失败样本、指标计算方法和测量边界。

## 8. 开题报告摘要草案

针对工业执行机构维护过程中异常动作难以复现、设备状态记录与现场视频相互分离的问题，本课题拟设计一套面向执行机构的状态监测与远程测试系统。系统以现有树莓派原生 MJPEG 低延迟视频链路为基础，结合 Modbus TCP 状态采集、动作状态机、命令确认与报警事件记录，实现设备状态、测试操作及视频证据的时间关联。首先建立具有限位异常、动作超时和通信中断注入能力的软件模拟工位，验证互锁逻辑、命令幂等性及异常恢复流程；条件允许时接入低压执行机构或教学 PLC 进行实物验证。通过动作耗时、报警检测延迟、通信恢复时间、视频年龄及测试完成率等指标进行量化评价，并分析采样周期、跨设备时钟偏差及网络抖动对结果的影响。课题重点为测控信息获取、测试流程设计与故障证据组织，不将视频识别作为安全控制依据，也不将模拟结果等同于真实设备测量性能。
