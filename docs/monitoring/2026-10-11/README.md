## 已部署

`http://192.168.3.19:8080/monitor/` 提供真实视频、主机状态、独立过期标记、趋势、规则事件及前后证据。原视频入口和协议保留。`pi-observer` 只读服务在本机 8092，前端代理在既有 8080。旧 `pi-industrial-gateway`、`pi-industrial-simulator` 停止且禁用开机自启，源码和数据未删除。

## 可复现数据

`matrix/` 为四轮时钟通道 ABBA 与十分钟完整 HMI 数值观测，`fault-results.json.gz` 为三轮真实采集暂停。原始 JSON.gz 不含图像。所有轮次保留，不只挑选正常轮次。`summary.json` 的时间为实际有效时间，HTTP 请求超时可能让它超过名义采样时长。

时延口径：发布至解码与驱动至解码是不同估计；驱动 SOE 标记未经光学标定。时钟余量不是可溯源不确定度；发送至接收不等于纯无线空口耗时。年龄是按时间采样，帧时延是成功解码帧样本。末尾未闭合停顿不包含在相邻帧间隔中，需一起检查年龄和无效校准。

四轮时钟对照没有证明独立时钟稳定降低视频时延。独立连接保留用于测量结构解耦；默认 decode 不变。当前 Wi-Fi 长尾仍存在，不得将此提交宣传为“完全解决卡顿”。本轮软件功能和通信性能分别验收，不互相代替。

## 网络定位

长尾复现时，PC 到 Pi 的 90 次 ICMP 探测有 10 次未在 1 秒内返回，已返回样本平均 150 ms、最大 880 ms。随后近同时的 90 次路由器探测：PC 0 丢失、平均约 2 ms、最大 20 ms；Pi 0 丢失、平均 92.776 ms、最大 930.229 ms。两个实验窗口不同，不把这三组当作严格同步逐包比较。

PC 到 Pi 实际路由为 WLAN 上的本地 /24，并未绕经 VPN。Pi 固件为 BCM4345/6、brcmfmac，读取的 PHY 速率 390 Mb/s，不代表应用吞吐。证据优先指向 Pi 与接入点一侧链路及其交互，但未区分 RF 干扰、接入点调度和固件内部排队。不能据此直接断言某个驱动存在已证实缺陷。

## Linux 队列层探索

另行进行原 fq_codel、`fq maxrate 40mbit`、恢复 fq_codel 各约 120 秒对照。修改前用 systemd 临时定时器设置 240 秒后恢复原队列；结束后已主动恢复并停止定时器，无永久配置变化。fq 的 maxrate 是每流上限，并非整个网卡总带宽上限。

| 配置 | fps | 发布至解码均值 | P95 | 年龄 P95 |
| --- | ---: | ---: | ---: | ---: |
| 原 fq_codel | 21.31 | 44.3 ms | 106.5 ms | 240.8 ms |
| fq 40 Mbit/s | 22.12 | 43.9 ms | 98.7 ms | 197.9 ms |
| 恢复 fq_codel | 23.58 | 36.7 ms | 91.0 ms | 179.8 ms |

恢复后优于试验配置，不足以证明 pacing 带来稳定收益，故不固化。三轮全部没有超过 1 秒间隔，只说明该窗口环境不同于此前长尾窗口。原始文件在 `pacing/`，与时钟 ABBA 分开。参数含义依据 [iproute2 官方手册](https://github.com/iproute2/iproute2/blob/main/man/man8/tc-fq.8)。

## 故障实验结果

每轮 docker pause 采集约 6 秒，解除后等 8 秒。三次触发时间分别 1655.3、1390.1、2258.5 ms，恢复分别 1567.6、1311.4、1172.1 ms。每轮均 1 次触发和 1 次恢复，前 10／后 5 样本完整，六张图像实际保存在 Pi，状态通道均 GOOD。只是进程暂停，不是电机故障或拔插试验；unpause 由脚本执行，不宣称内部看门狗解冻了暂停进程。
