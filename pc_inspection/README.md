# PC assembly inspection demonstrator

This is an **offline synthetic demonstrator** for a three-position assembly
inspection cell. It does not connect to a camera, PLCSIM, GPIO, or real
actuators. The existing Pi video services and their ports are untouched.

## Run on the PC

From the repository root:

```powershell
python -m pc_inspection.demo
python -m unittest discover -s tests -p test_pc_inspection.py -v
```

The PC needs Python, NumPy, OpenCV with GUI support, Pillow, and Tkinter.
The scenario selector switches between all parts present, slot 2 missing,
slot 3 misplaced, and slot 1 occluded. A decision is accepted only after
three consecutive matching frames. Occlusion and old frames are `UNKNOWN`;
none of `UNKNOWN`, `MISSING`, and `MISPLACED` can start or continue a cycle.
The Start, Reset, and Stop controls affect only the in-process simulator.

Event changes are written as numeric/label-only JSON lines in the gitignored
`private/` directory. Neither frames nor any PLC credentials are exported.
The displayed frame age is a same-process software age, not optical latency.

## Proposed 100-point PLC I/O schedule

`io_map_100.csv` is a point-by-point **planning document**, generated by
`python -m pc_inspection.io_plan`. It is not an imported TIA tag table, a
configured PLC project, or evidence that 100 devices are connected.

| Class | Points | Planned modules | Address range |
| --- | ---: | --- | --- |
| DI | 48 | 3 x 16-channel | I0.0-I5.7 |
| DO | 32 | 2 x 16-channel | Q0.0-Q3.7 |
| AI | 16 | 2 x 8-channel | IW64-IW94, step 2 |
| AO | 4 | 1 x 4-channel | QW64-QW70, step 2 |

Each of stations A (feeding/clamping), B (gluing), and C (inspection/sorting)
has 12 DI, 8 DO, and 4 AI. The remaining 12 DI, 8 DO, 4 AI, and 4 AO
represent shared cell services. One analog word is counted as one channel,
not 16 digital points. Signal names are unique, addresses do not overlap,
and all 100 rows have status `PLANNED_SIMULATION`. Exact module catalog
numbers, module start addresses, analog ranges, scaling, and CPU compatibility
must be checked in the eventual TIA V21 project before use.

The camera's three `VisionValid`/`SlotOk` decisions are separate task data
for the PLC logic, not additional physical I/O points. The simulated safety
chain and emergency-stop entries are **status models only**, not safety-rated
functions. No actual I/O modules or field devices are owned by this project.
The existing `FC_VisionInterlock.scl` covers only the initial vision interlock;
it does not yet consume or drive all 100 planned points. Neither the PLC
program nor an external plant simulator has been built for the full schedule.

## TIA Portal preparation

`FC_VisionInterlock.scl` is an older **draft simulation-only Boolean interlock**.
Its input contract is `VisionValid`, `Slot1Ok` through `Slot3Ok`,
`GuardClosed`, `StopRequest`, `MoveRequest`, and `GlueRequest`. Outputs are
`Ready`, `ConveyorEnable`, `GlueEnable`, and `Reject`. The conveyor and glue
outputs cannot both be true. Do not import or wire this draft to the current
project while the diagnostic-only integration is being validated. In a
separate, reviewed TIA Portal V21 project, add it to the CPU's **External
source files**, then use **Generate blocks from source** and compile. This
draft has not been compiled in TIA or executed in PLCSIM. Generating an FC
alone does not execute it: it needs an explicit OB1 call and mapped tags.
The Python window does not write PLC tags. The computer now has a working
Standard S7-PLCSIM V21 instance; Advanced external integration is not yet
available because its instance/license path has not been verified.

Before connecting real hardware, the PLC must independently detect a lost
vision heartbeat, apply physical safety interlocks, and control actuators
through a reviewed machine design. The PC's `VisionValid` bit alone is not
a safety-rated signal.

## First 16-input pilot

`first16_tia_pilot.md` defines the first TIA/PLCSIM exercise from the
100-point plan. `FC_AInputDiagnostics.scl` evaluates station-A input
diagnostics without driving actuators; `pilot_inputs.py` is a testable
Python reference model. The diagnostic FC is present in the separate TIA
project `E:\PLC\项目1\项目1.ap21` and has been exercised in Standard PLCSIM.

`FC_VisionDiagSim.scl` is a new diagnostic-only source for synthetic vision
events. Its outputs are `SimSampleQualified`, `SimMotionObserved`, and a fault
code, never an actuator command. `vision_sim.py` and `test_vision_sim.py`
provide a reference model and fault-injection tests. This new SCL source has
been imported and generated as `FC_VisionDiagSim [FC2]` in the isolated TIA
project copy at `docs/plc-operations/tia-sim-archive-extracted-20261023/`.
TIA source generation reported 0 errors and an optimized-block-access note.
An initial offline CPU software compile warned about reading an FC output
parameter inside the block; after computing with a local fault-code variable,
the isolated project compiled with 0 errors and 0 warnings.

`VisionScenarioSim.scl` adds `DB_VisionScenarioSim [DB3]` and a wrapper
`FC_VisionScenarioSim [FC3]` in that isolated project copy. The wrapper first
calls `FB_VisionSequenceSim [FB1]` through instance `DB_VisionSequenceSim
[DB4]` to calculate synthetic sequence freshness, then calls FC2 and writes
only DB diagnostic outputs. DB3 supplies synthetic `SampleSeq`, `BootTag`,
and `MaxStallTime` (default `T#500ms`); no Pi or external app writes them.
The isolated
`Main [OB1]` now calls FC3 in a separate network; the existing Network 1
remains unchanged. DB defaults fail closed: `SimulatedSource=false`,
`RoiVerified=false`, `FrameAgeMs=65535`, `MaxFrameAgeMs=250`, and
`SimFaultCode=90`. After regenerating the source, the isolated CPU software
compiled with 0 errors and 0 warnings. The isolated project has since been
downloaded to a separate Standard PLCSIM `Instance_3` and started in RUN;
the default station `SimState=90`, virtual conveyor/glue commands `FALSE`,
and vision/station fault codes `90` have been observed online. A bounded
synthetic input check on `DB_VisionScenarioSim.SimulatedSource` produced
`FALSE -> TRUE -> FALSE` with vision fault code `90 -> 10 -> 90`; station
state and commands stayed fail-closed. A second isolated online check set
`LinkOk=TRUE` while `QualityCode=0`, producing vision fault code
`90 -> 10 -> 20 -> 10 -> 90` as the source and link bits were set and then
restored; both bits are `FALSE` again, and station commands stayed `FALSE`.
This does not verify sequence, timer,
restart, physical I/O, or real camera-to-PLC behavior. The Pi configuration remains
`roi_verified=false`; a synthetic `RoiVerified=true` in a simulator does not
validate the real camera. `SequenceAdvancedWithinWindow` and `BootTagStable`
are now computed by the FB from synthetic sequence observations, not manually
held true. The Python reference and fault tests cover this logic, but PLC
scan/timer behavior and restart state have not been validated online. DB4's
offline Retain column is unchecked for its state and timer fields. See
`docs/plc-operations/PLC仿真操作记录.md`.

The Standard PLCSIM workspace has the original `Instance_2` running at
`192.168.0.1`, `Instance_1` powered off, and the isolated `Instance_3` loaded
and running at `192.168.0.222`. The backed-up isolated TIA project was
compiled with 0 errors and 0 warnings and archived separately. The
[S7-PLCSIM V21 manual, sections
5.1-5.2](https://cache.industry.siemens.com/dl/files/161/109997161/att_1348284/v1/S7-PLCSIM_Help_en-US.pdf)
states that a download with no configured same-IP instance chooses a powered-on
unconfigured instance. TIA found generic `CPUcommon` at `.222`, but its
certificate reported an address mismatch and an unknown self-signed issuer.
The certificate did not uniquely identify `Instance_3`, so the first attempt
was cancelled. A later power-off/power-on test of only `Instance_3` made TIA's
`.222` search result change one to zero to one while `Instance_2` remained RUN.
With that target-identity check, the isolated project was loaded to
`Instance_3`; a new SIM table bound only to this instance monitored default
`SimState=90`, conveyor/glue commands `FALSE`, and vision/station fault codes
`90`. A subsequent single-input diagnostic test was restored to its original
`FALSE` value. The certificate warning was accepted for this local simulation
only, not as evidence of production trust.
This is not Pi-to-PLC communication or a complete PLC test. See the operation
record, sections 41-44, for screenshots, the target-identity test, and the
reversible diagnostic tests.

## Repeatable synthetic diagnostic trace

`plcsim_acceptance_v1.json` is a human-readable 22-step input/expected-output
trace for the diagnostic-only DB3/FB1/FC2 path. It covers the fail-closed
default, two-sample arming, sequence stall and recovery, age and quality
boundaries, link loss, boot-tag change, synthetic ROI and camera faults, and
non-synthetic-source rejection. Its `at_ms` values drive the Python reference
model; they are **not** measured PLC scan or timer timestamps. The JSON is
**not** a Siemens SIM table or Sequence import file. The [S7-PLCSIM V21
manual, sections 6.2-6.3](https://cache.industry.siemens.com/dl/files/161/109997161/att_1348284/v1/S7-PLCSIM_Help_en-US.pdf)
only documents importing files exported by S7-PLCSIM/TIA, so no undocumented
import format has been invented here.

The separate virtual CPU and a new SIM table bound only to `Instance_3` are now
proven. For future synthetic steps, map JSON input names to DB3 fields
(`sample_seq` to `SampleSeq`, `boot_tag` to `BootTag`, `max_stall_ms` to
`MaxStallTime := T#500ms`, etc.); monitor `SimFaultCode`,
`SimSampleQualified`, and `SimMotionObserved`. Use consistent modification for
the initial synthetic baseline, then change one field per step and compare
the observed diagnostics. For the stall case, hold `SampleSeq` constant for
more than 500 ms after arming and record the actual virtual CPU timing; do not
infer exact timer behavior from the JSON schedule. A native PLCSIM Sequence
may be built inside the application later and bound to the same isolated
instance. Do not bind a table or sequence to the existing `Instance_2`, force
physical I/Q addresses, or treat `roi_verified=true` in this fixture as a
real camera validation. Restore `SimulatedSource=false` when finished.

Run the offline reference check with:

```powershell
python -m unittest pc_inspection.test_vision_pipeline_sim
```

## Virtual conveyor/glue station (isolated TIA and PLCSIM pilot)

`FB_VirtualStationSim.scl` is a simulation-only station controller. It consumes
synthetic inputs and the diagnostic `SimSampleQualified` / `SimMotionObserved`
values from DB3. Its outputs are `SimState`, `SimConveyorCmd`, `SimGlueCmd`, and
`SimFaultCode`, written only to a simulation DB. The saved isolated TIA copy
now contains `FB_VirtualStationSim [FB2]`, its instance
`DB_VirtualStationSim [DB6]`, `DB_VirtualStationScenarioSim`, and wrapper
`FC_VirtualStationScenarioSim [FC4]`. `Main [OB1]` calls FC4 in Network 3,
after the vision diagnostic FC3 in Network 2. A CPU software compile after
the OB1 edit reported 0 errors and 0 warnings. The isolated project was
subsequently downloaded to `Instance_3` and put in RUN; a SIM table bound to
that instance monitored default `SimState=90`, both virtual commands `FALSE`,
and vision/station fault codes `90`. No dynamic sequence has been verified
online. This is not Pi-to-PLC data
exchange or a physical machine test. There is no physical `Q` mapping or real device
connection. Do not connect the virtual command bits to real outputs.

The pre-import, post-OB1, and isolated-IP TIA archives are
`docs/plc-operations/tia-sim-prestation-20261023.zap21` and
`docs/plc-operations/tia-sim-poststation-20261023.zap21`, plus
`docs/plc-operations/tia-sim-isolated-ip-222-20261023.zap21`. The original
`E:\PLC\项目1\项目1.ap21` was not edited. See
`docs/plc-operations/PLC仿真操作记录.md`, sections 39-42, for the sequence and
screenshots.

The pilot state values are 0 idle, 10 virtual conveying, 20 virtual gluing,
30 complete, and 90 latched fault. A fresh Start edge requires qualified
synthetic vision, observed motion, virtual guard/ready signals, and a part
not already at the glue station. `AtGlueStation` ends conveying and starts
the virtual glue dwell. Stop, open guard, lost vision qualification while
active, missing readiness, and move timeout latch a fault and clear both
virtual commands. Reset requires a new edge and ready inputs; a held Start
cannot silently restart. This is a process simulation, **not** a safety PLC
function or a design for real actuators.

`virtual_station_sim.py` mirrors this scan contract for offline tests.
`test_virtual_station_sim.py` covers a full cycle, timing, faults, reset,
timer preset latching, and a synthetic sequence-stall-to-station-fault path.
`plcsim_station_acceptance_v1.json` fixes a separate 28-step synthetic
station timeline: start-edge rejection, conveyor-to-glue transition, dwell,
vision and guard faults, arrival-at-timeout priority, and non-synthetic
source rejection. The test checks every expected state, command and fault
against the Python reference. Its `at_ms` values are reference-model time,
not measured PLC scan times; it is **not** a Siemens import file and its
`plcsim_status` remains `NOT_RUN_IN_PLCSIM`.
The reference model cannot prove that the SCL behaves the same in a virtual
CPU. Offline SCL compilation, isolated target identification, download, RUN,
and a read-only default-state observation are verified; timer, scan, restart, and
fault behavior still require dynamic testing on `Instance_3`. The current
100-point I/O plan remains a planning document; this pilot does not implement
its other station signals. Do not modify or download to the existing
`Instance_2`.

```powershell
python -m unittest pc_inspection.test_virtual_station_sim
```

In the existing SIM table bound to `Instance_3`, add the remaining FB inputs
and outputs in its instance DB, apply each JSON `set` change, and
compare stable states. Map `max_move_ms`/`glue_dwell_ms` to SCL `TIME` values;
allow for real scan and timer scheduling rather than expecting a transition
at the exact JSON millisecond. Never apply this trace to the original
`Instance_2` or to physical I/Q tags.

## Visible software workcell

`virtual_workcell_demo.py` adds an animated PC-only conveyor and glue station.
It runs `VirtualWorkcell`, which joins the synthetic camera sequence/vision
diagnostics, `VirtualStationSim` controller reference, and a `VirtualPlant`.
The plant advances only under `SimConveyorCmd`; reaching the glue position
feeds a simulated arrival sensor back to the controller. Glue appears only
under `SimGlueCmd`. Freezing synthetic frames, opening the simulated guard,
stopping, or withholding arrival feedback demonstrate fail-closed behavior.
A UI stall longer than 250 ms faults the synthetic link and does not replay
unobserved conveyor travel. The current viewer is explicitly labeled
"software model / not connected to PLCSIM / no physical output".

```powershell
cd _semantic_adaptive_v2
python -m pc_inspection.virtual_workcell_demo
python -m unittest pc_inspection.test_virtual_workcell
```

This app opens a local Tk window and **no new webpage or TCP listening port**.
It does not read the Pi camera, write any PLC/PLCSIM DB, or implement the full
100-point plan. Its interface (`StationInputs` / `StationOutputs`) is a
candidate contract for later PLC-in-the-loop verification, not evidence that
the Standard PLCSIM instance is already linked. For an industrial migration,
the actual vision scene, communication interface, PLC program, safety system,
and real I/O must be validated separately. Siemens describes [virtual
commissioning](https://cache.industry.siemens.com/dl/files/095/109975095/att_1299171/v2/109975095_VC_PlantSimulation_PLCSIMAdv_DOC_V10_en.pdf)
with a process model and PLC simulation; its [product comparison](https://docs.tia.siemens.cloud/r/simatic_s7_1500_et_200mp_manual_collection_enus_21/comprehensive-information/cpu-function-manuals/s7-plcsim-advanced/product-overview/s7-plcsim-products)
lists external co-simulation APIs under Advanced, not the current Standard
Softbus setup.

Official Siemens reference: [Generating blocks from external source files](https://docs.tia.siemens.cloud/r/en-us/v21/creating-and-managing-blocks/using-external-source-files-for-stl-and-scl/generating-blocks-from-external-source-files).
