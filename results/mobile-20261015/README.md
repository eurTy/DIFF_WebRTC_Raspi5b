# 手机外网优化记录：2026-10-15

## 验收边界

本轮保留原 8089，新增 8090。用户实际使用 iPhone、4G、Tailscale 验证。电脑浏览器模拟手机尺寸不等于 Safari 兼容性测试，后者依靠用户实机反馈。没有光学曝光到屏幕测量，不提供此类精确延迟承诺。

## 手机现场证据

用户先确认新版本“能播放，画质和连续性有改善”，随后给出 JPEG 延迟观察范围 80–240 ms、H.264 120–400 ms。不能将这个范围写成均值、P95、严格 A/B 或相同时间段的码率因果对比。

四张用户截图（不收录现场图像）的数值如下：

| 编码 | 当前帧龄 ms | 最近呈现延迟 ms | 显示 fps | 播放缓冲 ms | 有效负载 Mbps |
|---|---:|---:|---:|---:|---:|
| H.264 | 449.1 | 149.1 | 9.5 | 0.0 | 1.064 |
| H.264 | 280.2 | 228.2 | 13.0 | 129.8 | 1.389 |
| JPEG | 138.2 | 94.2 | 6.5 | 不适用 | 1.489 |
| JPEG | 125.2 | 100.2 | 7.0 | 不适用 | 1.494 |

这说明 H.264 在这些截图中帧率较高，而 JPEG 最近呈现延迟较低；既不能认定 H.264 全面胜出，也不能忽略 JPEG 的低帧率。重点块已随完整帧更新，不再以数秒前的单块刷新时间代表当前画面，但仍没有真实工业清晰度真值。

## 被拒绝的候选

随后试验了按实际采集时间间隔生成 H.264 媒体时间戳。电脑单元解码、浏览器测试通过，用户却反馈“延迟表现更严重”。立即回退到 `semantic-mobile-v05:phone-before-timeline-20261015`。这次修改不在最终保留源码中，不能描述为成功优化。

`rejected-timeline-browser.json` 仅保留其电脑测量反例；`rejected-timeline-phone-probe.json` 的 45 秒轮询窗口没有观众/有效显示报告，不能用该文件计算手机延迟。候选源码归档在本地忽略目录 `runtime/mobile-v05-rejected-capture-timeline.tgz`，不自动部署。

## 电脑合成与局域网结果

- `accepted-browser-local.json`：保留版本的电脑合成输入，390×844 和 1440×1000 两种尺寸；各自运行 H.264/JPEG，真实解码、非空画面、暂停恢复通过，没有 pageerror 或横向溢出。H.264 约 16.1 fps，当前帧龄 P95 约 134–138 ms；JPEG 约 6.2 fps。不是 4G 成绩。
- `early-browser-pi-lan.json`：启用有界字节信用之前的树莓派实机 LAN 浏览器验证，保留作阶段记录，不冒充最终版本或手机蜂窝结果。
- `quality-paired-pc.json`：seed 7 合成输入，90 帧，统一配置 2400 kbps/20 fps，比较常规 H.264、任务背景预滤波 H.264、v0.4 JPEG。实际输出码率不完全相同，因此不能只凭跨编码器 PSNR 排名得出等码率收益。

在该合成任务上，任务 H.264 与全景 H.264 相比，重点 PSNR 从约 30.98 dB 到 34.46 dB，但背景从约 27.67 dB 降到 24.69 dB；实际码率约 2066 与 2007 kbps。结论仅为“此场景下把部分背景质量换给任务区域”，不是全画质无损提升、工业检测准确率提升或通用算法优势。

## 后续验收顺序

1. 先保持 JPEG 低延迟入口可用，避免持续换方案使用户失去基线。
2. 另开独立的标准 RTP/WebRTC 媒体实验，明确 UDP/TURN/私有网可达条件。
3. 在相同输入、相近实际码率下，至少记录数分钟的帧龄分布、冻结比例、帧率、重点与背景质量、重连和失败段。
4. 只把手机复核通过的候选提升为默认，失败样本与回退原因保留。
