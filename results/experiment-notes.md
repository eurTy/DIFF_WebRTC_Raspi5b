# 实验过程说明

1. `rd-pc.json`：电脑离线预实验，帧号步长 7，调度时钟步长 100 ms。树莓派正式配对改为帧号步长 3，与 30 fps 输入、10 fps 调度一致。两者不合并比较 CPU 性能。
2. `network-pc.json`：电脑链路预实验，8 s 正式窗口、2 s 热身、每场景一次。末端一次接近窗口结束的 timeout 记录受到 Windows 定时分辨率影响；后续将窗口结束容差由 10 ms 改为 50 ms，不回写旧结果。
3. `network-pi-fixture-pilot.json`：与浏览器验收并发的部分试验，用于发现快速重连资源释放问题；主动终止，主表排除。
4. `network-pi-fixture.json`：第一轮正式 24 单元，两个纹理场景，每单元 3 s 热身、12 s 正式窗口。
5. `network-pi-confirmation.json`：第二轮改变策略顺序，条件与第一轮相同。第 8 个单元在开始校时时发生一次 TimeoutError，原运行脚本退出，已完成的 7 个单元仍在 JSON 中。后续加入有记录的有限重试和断点续测，原 7 个单元不重跑或覆盖。这次原脚本未记录到 JSON 的失败以本说明保留；后续失败由 setup_failures 数组记录。
6. 校时未完成的尝试不能获得可靠单向延迟，作为不完整尝试单独报告。重试获得的有效单元不代表失败从未发生。成功会话内的连接关闭、无帧和剩余观察窗口则均保留在时间覆盖率分母内。
7. `feedback-pi-fixture.json`：动态区域策略下的单次确认与五样本中值反馈消融。三档预算、两个纹理场景、两种反馈，每个条件重复两次，共 24 单元；每单元仍为 3 s 热身、12 s 正式窗口。随机顺序种子为 20261015。
8. `feedback-pi-live.json`：只读摄像头接入下，在 1200 kbps 进行两种反馈各两次补充测量，不计算没有真值支持的任务分数。与合成输入、四策略基线分开汇总。
9. 最终浏览器验收第一次使用固定 500 ms 间隔检查像素变化，出现两次截图仍为同帧的断言失败；修正为最多 10 s 等待实际像素变化，再进行独立验收。此修正仅影响功能测试，不改变任何网络实验数据或性能门限。
10. 新增的非法区域交互测试发现：运行中的正常帧会立即清除参数错误提示。最终网页区分源错误与参数错误，只在源恢复时清除源错误；参数错误保留到下一次成功连接。传输算法未改变。
11. 反馈消融完成后，真实输入未支持中值模式的默认替换，最终网页及服务器的缺省反馈恢复为 `single`。实验 runner 始终显式请求对应反馈，因此缺省值修改不改变上述实验条件。该变化以及网页提示修复使最终源码摘要与实验时摘要不同，不能据此声称所有文件逐位相同。

第一轮和第二轮之间的发送端编码器、区域打分和预算反馈算法没有改变。修改涉及连接关闭处理的回归覆盖、网页区域校验、实验溯源和结果记录。所有正式数据都来自同一套任务算法，不能将额外的两轮混称为大样本统计证明。

早期 runner 的 `receiver_source_sha256` 是每个检查点读取的工作目录文件摘要；第二轮续测过程中补充了脚本异常捕获和窗口边界判断，因此该字段不能视为已加载 Python 字节码的精确摘要。发送端编码器未变化。后续 runner 改为启动时冻结文件摘要，并标记 `source_hash_snapshot=run_start`；已有原始 JSON 不回写。论文引用的是各完整结果文件的 SHA256，未声称容器二进制逐位可复现。
