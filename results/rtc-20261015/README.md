# WebRTC 独立实验记录（2026-10-15）

## 文件范围

- `browser-local.json`：最终增量 ICE 版本的本机 Edge 合成源验证，390×844 和 1440×1000；包含逐帧软件时间戳估计与数值采样，不含摄像头图像。
- `browser-paced.json`：进一步修正采样周期后的同平台复测，不覆盖上一轮。
- `pi-turn-tcp.json` / `pi-turn-udp.json`：明确禁止 host socket 绕过后的树莓派中继验证，只含帧数、尺寸、所选候选类型及帧率。
- `initial-idle-probe.json`：首轮 90 秒轮询，无活动观看者，不可用于手机延迟统计。
- `phone-turn-tcp-probe.json`：手机 TURN/TCP 测试等待窗口的状态轮询。是否有有效样本必须同时检查活动会话、报告更新时间和帧率，不能将空窗口报告成播放成功。

## 已有证据

本地浏览器测试均收到 1280×720，零页面错误、零横向溢出，暂停后恢复通过。此轮 P50 44.29 / 46.02 ms，P95 49.75 / 50.07 ms；这些都是电脑合成源软件段延迟，不代表手机 4G。

采样修正后，本机浏览器 P50 为 46.73 / 41.83 ms，P95 为 54.80 / 49.68 ms；仍为约 16–17 fps。树莓派严格中继检查实际共享输入，TURN/TCP、TURN/UDP 各解码 35 帧，约 20.21 / 19.82 fps，确认选中的本地候选是 relay。未保存帧内容。它不能替代手机端可达性验证。

最早标为“TURN 测试”的 35 帧检查实际选中了 host，不能证明中继；增加实际候选断言后暴露此问题，随后测试中禁止创建本机 host socket，才获得上面的严格中继结果。对 Docker IP 的 TURN 请求曾按白名单被 403 拒绝，最终 answer 只公告可达的私有 IPv4，不放开白名单来掩盖问题。

首轮手机直接 ICE 连接失败：页面加载和 WebSocket 信令可达，客户端支持 RTCPeerConnection；服务端停在 `connecting/checking`，手机帧率为 0。后续以私有 TURN 和增量 ICE 继续排查；在手机确认出画面及收到有效反馈前，不宣称已经降低其延迟。

旧版 8089/8090 及旧 Tailscale 接入容器的镜像、启动时间已核对，本轮未改动或重启。

## 可复现检查

全量 Python 测试 58 项通过。单元测试的 ICE 只使用 loopback 避免 Windows 网卡变化污染结果；真实接口路径另由浏览器和树莓派检查。一次 Windows Proactor UDP 关闭测试暴露了会话清理等待，现已加两秒关闭上限与回归检查，不能隐藏这类负面结果。

技术路线、隔离部署、测量公式和未完成项见 `experiment_v06/README.md`。WebRTC 是既有协议，不当作论文原创；本阶段也没有声称已完成动态语义调度或真实工业任务验证。
