# 0.3.0 收敛、恢复与传输对照

所有延迟均为软件时间戳估计，不是光学端到端延迟。旧实验不覆盖，摄像头图像不上传。本目录保留成功与失败结果。

## 弱网配对结果

`paired-stress.json` 完成十二个单元：配置 1200 kbps / 10 fps，独立 TCP 字节中继限制 128 或 512 kbps，三种纹理（种子 6/7/8）、两种反馈策略；随机顺序，每单元预热 3 秒、正式 20 秒。端点是 Python JPEG 解码完成，普通桌面负载未完全隔离。分组数字为三单元平均，P95 是各单元 P95 的平均，不是合并样本分位数。

| 实际链路 kbps | 策略 | fps | P95 ms | 新鲜采样占比 ≤250ms | 新鲜任务代理分数 |
|---|---|---:|---:|---:|---:|
| 128 | single | 8.32 | 124.83 | 100.00% | 0.000 |
| 128 | realtime | 8.10 | 125.09 | 100.00% | 0.000 |
| 512 | single | 8.35 | 127.08 | 100.00% | 0.514 |
| 512 | realtime | 8.48 | 127.46 | 99.67% | 0.470 |

结论：相对于 0.2.0 开发记录中 128/512 kbps 的 260/172 ms，本轮新策略已回到同轮单帧基线附近；前后运行环境不是严格控制，不把跨轮差值当作普遍性能提升比例。512 kbps 任务代理分数仍低约 4.5 个百分点，高纹理单元差异更大；128 kbps 两者任务分数都是零。不能宣称全指标占优，也不能把高新鲜覆盖率等同于细节可辨。

### 保留的失败候选

- `candidate-context-regression.json`：背景偏好候选，九个完成单元，主动终止后 `complete=false`；部分任务分数明显下降。仅供故障分析，不作最终验收集。
- `candidate-mixed-acks.json`：上下文回退后、快慢 ACK 计数未分离的候选，八个完成单元，`complete=false`；继续暴露任务分数下降。
- 最终十二单元不覆盖上述候选。`experiments.summarize_convergence` 独立重算每个单元的时间分母、任务得分与载荷速率，汇总在 `summary.json`。

## 旧原生 JPEG 传输路径对照

`transport-comparison.json` 只访问旧服务，不修改旧文件。WS、WebRTC、WebRTC、WS 各测 60 秒；全部使用原生 1280×720 摄像头 JPEG，端点为浏览器 `img.decode` 完成。

| 路径 | 实际 fps | 载荷 Mbps | P95 ms | 新鲜采样占比 ≤250ms |
|---|---:|---:|---:|---:|
| WS 第一次 | 25.45 | 19.66 | 80.70 | 99.50% |
| WebRTC 第一次 | 28.81 | 22.24 | 524.62 | 69.17% |
| WebRTC 第二次 | 28.80 | 22.23 | 514.99 | 75.83% |
| WS 第二次 | 25.83 | 19.87 | 78.32 | 99.83% |

视频数据通道实际是 `ordered=false, maxRetransmits=0`，控制通道可靠有序。这个结果说明当前实现不能通过“不重传”三个字保证低延迟；发送节奏、分片、重组与队列仍需一起设计。两条路径码率与节奏不同、场景与 Wi-Fi 未固定，不能推导 TCP 普遍优于 WebRTC，更不能与新版 2.4 Mbps 语义档做同画质比较。

两个 WebRTC 会话结束后旧网关按既有 `Recycling gateway session; supervisor will restart` 逻辑退出并重启；Docker 记录两次退出码 1，之后恢复运行。这不是本轮更改旧代码或执行重启命令造成的。ICE 地址不保存在公开结果中。新服务本轮没有换用 WebRTC。

## 恢复、配置与部署

- `startup-pi-final.json`：首次加载时服务不可用可恢复；禁用状态接口仍能启动；刷新恢复已应用配置；损坏与禁用存储均有退路；暂停取消首次重试。五项检查无浏览器错误。
- `recovery-local.json`：受控断流后的恢复约 1.32 秒，迟到帧计数生效，暂停取消重连；只作用于测试查看端，不是实际射频中断。
- `recovery-pi-calibrated-20261014.json`：等待校时完成后进行三项实机验收，受控断流解除后约 1.287 秒恢复，迟到帧丢弃 2 帧，暂停取消重试。更早一次独立续测为 357 ms，不能只选择更快的一次。
- 测试失败也保留：10 月 13 日一次实机尝试在首次收帧阶段超时，原因未定位；10 月 14 日 `recovery-clock-precondition-failure.json` 在校时尚未完成时注入断流，断言数字帧龄失败，属于测试前置条件不足。修正脚本不是修复真实无线丢包的证据。
- `deployment-audit.json`：运行代码与部署目录一致，旧 39 个规范源文件未改变，只读输入、非 root 视频容器与原权限保持。Docker 内存限制为 0 不能解释为零内存占用。
- 本地回归覆盖业务逻辑、协议、网络、连续帧龄、配置存储和浏览器布局；实机核心后端测试在部署时通过。最终测试数量与检查记录见 `validation.json`。
- 现场旧采集器在摄像头断开后停机约半小时，本轮只启动已退出的采集容器。新增主机恢复 timer 的作用与停止方法见 `../../ops/README.md`；没有人为拔插验证，不能写成完整热插拔验收。

## 容量阶跃与连续运行

阶跃轨迹为 1200 → 128 → 512 → 1200 kbps，仅改变本机实验中继，不修改主机网卡或树莓派 Wi-Fi。原始阶段结果保存于 `capacity-steps.json`；这是额外的动态探索实验，不替代固定容量配对结果。

两种反馈在这次探索中均没有会话失败。容量降到 128 kbps 的十秒阶段，新鲜采样占比均为 94%，不能宣称突降瞬间没有停顿。恢复至 1200 kbps 后，新策略在最后十秒的预算由约 6736 B 增至 14107 B，单帧基线由约 6283 B 增至 11709 B；显示帧率均约 9.2 fps，P95 均约 96 ms。它说明该轨迹下具备恢复能力，不证明所有 RTT、丢包和复杂场景都能同样恢复。

长测每分钟导出一次并按事件时间去重，总数须与显示数加丢弃数一致。独立复核从逐帧绘制完成时刻计算新鲜时间积分，不直接把界面每 250 ms 更新的帧龄当作连续时间测量。`complete=true` 只表示计划采集结束，不等于稳定性达标。

10 月 13 日长测因会话中断只留下 1505.69 秒，保存为 `endurance-interrupted-20261013.json.gz`，`complete=false`。`summary-interrupted-20261013.json` 独立重算：28987 帧、19.25 fps、P50 46.67 ms、P95 71.71 ms、无丢弃与重连、新鲜时间占比 99.728%、最大显示间隔 443.8 ms。这个结果只能描述这段观察，不能宣称完成半小时或跨天稳定。

10 月 14 日完成计划 1800 秒观察，采样首尾跨度 1799.924 秒，保存为 `endurance-network-failure-20261014.json.gz`。这是**完成采集但稳定性失败**，独立汇总位于 `summary.json`：

| 指标 | 本轮无线异常观察 |
|---|---:|
| 全部到达记录 / 显示 / 丢弃 | 16770 / 16172 / 598 |
| 重连次数 | 85 |
| 显示帧率 | 8.98 fps |
| 已校准到达帧软件延迟 P50 / P95 | 42.33 / 331.37 ms |
| 到达帧最大延迟（含已丢弃帧） | 2919.18 ms |
| 最大两次显示间隔 | 69061.8 ms |
| 连续新鲜时间占比 ≤250ms | 48.397% |
| 连续帧龄 P95 | 13134.67 ms |
| 测量窗口内未知延迟的显示帧 | 201 |
| 监控请求错误 | 13 |

最大延迟帧确实被拒绝，窗口内已校准的显示帧最大延迟约 499.88 ms；这并不消除无新帧期间的冻结。未知延迟不能等同于零或自动算入新鲜时间。UI 每 250 ms 刷新的帧龄统计与独立积分不同，论文使用上述独立复核值。期间有只读网络探测、短时第二观看端恢复验收和隔离容器回归，未改运行视频代码或网络参数，因此也不作为单一变量因果实验。

正式连续运行期间包含短时第二观看端的浏览器与配置恢复验收，亦包含普通桌面上的本地实验负载，不是完全空载、固定场景的性能基准。一次早期试运行因监控地址不可达和候选更换主动停止，不作为完成的长测，保留 `pilot-incomplete.json.gz`。

## 10 月 14 日无线异常排查

用户确认未主动重启、调整供电或网络。本轮没有执行重启或改网络参数。读取到的 boot ID 与前晚不同，启动初期墙上时间与后续校准时间不一致，因此 Docker 显示的“Up 16 hours”不能当作单调运行时长；无法从现有日志确认重启原因。

- 早期交互式探测：电脑到树莓派 15 次 ping 仅 1 次收到、14 次超时，SSH 曾被重置；电脑到网关随后 10 次全部收到。属于不同时段的观察，不能当同步因果实验。
- `network-pc-20261014.json`：后续 20 次到网关全部成功，最大 15 ms；20 次到树莓派全部成功但最大 393 ms；状态请求出现约 1172 ms 尖峰。该初版探测使用 `time.monotonic`，Windows 时间粒度较粗，不用其中小数评价亚毫秒性能；工具随后改为 `perf_counter`，不覆盖原始结果。
- `network-pi-20261014.json`：本机状态请求约 1.3–6.2 ms；20 次到网关全部成功，最大 34.46 ms；20 次到电脑全部收到但平均 907.78 ms、最大 2312.02 ms。供电降频标志 `0x0`、无线省电关闭。短时邻居表核对一致，重复地址探测没有响应，不能据此永久排除地址冲突。
- `loopback-stress-20261014.json`：树莓派本机两策略、各 20 秒、1200 kbps 应用中继，约 9.75/9.80 fps、P95 134.27/133.77 ms、无会话失败。它包括人为串行化，不是未整形的本机最低延迟，也不是浏览器端点。

结论：有独立于视频编码的通信异常，不能把所有卡顿归因于编码；具体接入点/驱动根因尚未确定。没有关闭电脑代理或 VPN，没有改无线网卡、路由器、内核或旧项目。`tools/network_probe.py` 可以复测，代理仅在该探测进程内绕过，系统设置不变。下一步需要另一终端或另一接入点进行路径隔离，不要求额外开发板。

## 复核命令

```sh
python -m unittest discover -s tests -v
python ops/test_capture_guard.py
node tests/protocol.cjs
node tests/settings.cjs
python -m experiments.summarize_convergence --soak results/convergence-20261013/endurance-interrupted-20261013.json.gz --allow-incomplete --output results/convergence-20261013/summary-interrupted-20261013.json
python -m experiments.summarize_convergence --soak results/convergence-20261013/endurance-network-failure-20261014.json.gz
python tools/network_probe.py --url http://192.168.3.19:8088/api/status --targets 192.168.3.1 192.168.3.19 --count 20 --output runtime/network-check.json
```

浏览器脚本需要 Playwright 和已安装的 Edge。新算法、不同编码方案以及长时间实机观察仍不足以证明工业认证、光学真实延迟、全带宽画质保证或 AI 语义理解；旧论文保持原样，新技术路线独立保存在 `../../docs/technical-route-v030.md`。
